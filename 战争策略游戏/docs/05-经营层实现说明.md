# 经营层实现说明 v1.0

> 对应设计：文档 01 §5。代码：`src/game/economy.ts`，测试：`tests/economy.test.ts`（46 项）。
> 全部为纯函数，无随机，同输入必同输出。

---

## 一、实现的规则

### 1. 三资源与派生量

| 量 | 公式 | 说明 |
|---|---|---|
| 每日粮产 | `(人口/20万) × 170 × (1 - 税率×0.5) × (1 + (据点等级-1)×0.15)` | 税率越高，种田的人越少 |
| 每日金收入 | `(人口/20万) × 55 × 税率 × (1 + (据点等级-1)×0.2)` | 税率直接决定收入 |
| 后方驻军日耗 | `驻军/1000 × 10` | 与 combat.ts 的 `supplyCapacity` 同源 |
| 前线日耗 | `前线兵力/1000 × 10 × 3` | **前线消耗是后方的 3 倍**（战场无就地补给）|
| 可征兵数 | `人口 × 0.10 × (民心/50)` | 文档 §5.3 的核心公式 |
| 驻军上限 | `据点等级 × 5000` | |

**初始值**：人口 20 万，民心 50，粮 3000，金 800，兵源 0，税率 0.1，据点 1 级。

### 2. 粮为 0 的连锁反应

```
粮 = 0 → 每日民心 -6
     → 民心跌 → 可征兵数跌 → 下次战斗兵力不足
```

这是「你能不能打这场仗」成为真实问题的支点。实测：6 万驻军 + 粮 200 时，60 天内粮耗尽、民心跌破初值。

### 3. 民心变化来源

| 事件 | 民心 |
|---|---|
| 上阵凯旋、低伤亡 | +6 起（每 10% 额外伤亡 -2）|
| 败还 | -10 起（同上惩罚）|
| 粮尽 | -6 |
| 强征超上限 | 按超出幅度 -1 ~ -30 |
| 税率 > 0.2 | 每日 -1（调税时）|
| 任务奖励 | 按任务定义（-4 ~ +12）|
| 人口自然增长 | 每日 +0.04% × (民心/50) |

**关键设计**：败绩打击（-10 起）大于胜利激励（+6 起），且伤亡会额外扣减——"惨胜不如小胜"。

### 4. 据点基建

- 等级 1~5，每级提高驻军上限、粮产、金收
- 升级需 `金 = 等级×200`、`粮 = 等级×150`，工期 6 天
- **升级期间防御系数 0.8**（守城战 -20%）——这是「投资 vs 战线」的时间博弈
- 升级中不可再次升级

### 5. 任务系统

三类任务各3 个：

| 类别 | 任务 | 时长 | 奖励 |
|---|---|---|---|
| 军事 | 剿灭山匪 / 守卫粮道 / 边境巡哨 | 3/4/5 日 | 兵源、粮、金 |
| 经济 | 修筑渠堰 / 开采盐井 / 开辟屯田 | 4/5/6 日 | 粮、金 |
| 内政 | 整顿吏治 / 轻徭薄赋 / 征兵演练 | 3/2/5 日 | 民心、兵源 |

**关键约束**：**同时只能推进 2 个任务**。这是取舍的来源——选军事就放弃发展，选发展就可能错过战机。

**失败后果**：只有数字惩罚与连锁影响（民心低 → 可征兵少 → 下次战斗兵力不足），不触发任何剧情。符合纯系统驱动准则。

## 三、测试实跑抓到的 5 个真实缺陷（已修）

这些都是设计或实现层面的实际错误，由测试暴露：

### 缺陷 1：税率越高，金收入反而越低

**原因**：初版 `dailyGoldIncome` 里写的是 `labor × 55 × (1 - taxRate × 1.5)` —— 把税率当成了劳动力折损。税率 0.1 时系数 0.85，税率 0.25 时系数 0.625。

**后果**：提高税率是纯亏损，税率这个决策维度完全失效。

**修法**：税率只影响两件事——金收入（正比）与民心（负相关）。劳动力由人口独立决定。
```
金收入 = (人口/20万) × 55 × 税率 × (1 + (据点-1)×0.2)
粮产   = (人口/20万) × 170 × (1 - 税率×0.5) × ...
```
现在税率 0.25 的金收入是0.1 的 2.5 倍，而粮产略降、民心受损——**有真实的取舍**。

### 缺陷 2：任务永远无法完成

**原因**：为满足纯函数要求，`advanceDay` 不修改 `state.availableTasks` 里的 `durationDays`，而是每日本地计算 `remainingDays[id] = task.durationDays - 1`。但 `task.durationDays` 本身从不改变，所以剩余天数恒为 `durationDays - 1`，永远 > 0。

**修法**：把剩余天数存进 state（`taskDaysLeft: Record<string, number>`），开始任务时写入 `durationDays`，每日递减，归零时发放奖励并移除。

**这暴露一个通用陷阱**：**纯函数 + 跨调用可变状态，必须显式把状态存进 state，不能依赖计算推导。**

### 缺陷 3：上阵反而让粮增加

**原因**：前线耗粮按 `lastBattleFoodLoss × 0.08` 计算（行军一次性耗粮的 8%），而初始行军耗粮只有 30 粮 → 每日 2.4 粮，而每日粮产 234。

**修法**：前线耗粮改为**按人数计算**而非按行军耗粮折算，并加 3 倍战场系数。
```
前线日耗 = 前线兵力/1000 × 10 × 3
```
现在 3 万人在前线每日耗 900 粮，粮产 154——**大军作战真的会把家底吃空**。

### 缺陷 4：粮产过高，撑得住任何规模驻军

**原因**：粮产 234/日，而后军日耗仅 `兵力/100×10`。即使 6 万驻军（600 粮/日）也能长期撑住，"粮为0 则溃散"的支点形同虚设。

**修法**：粮产从 260 降到 170，同时前线系数 3 倍。现在 6 万驻军净亏 450 粮/日，粮耗尽成为真实威胁。

### 缺陷 5：测试 mock 缺陷（两处）

不是生产代码问题，但会导致假阴性：
- `keyAt: () => 'hill'` 把**所有**位置都变成山地，包括本该在平原的守方 → 改为按坐标区分
- 断言方向搞反：对称编制下每方伤亡取决于**对方**地形，不是自己

## 五、平衡基线（实测）

| 场景 | 结果 |
|---|---|
| 初始状态静置 10 天 | 粮稳定增长，可持续 |
| 3 万人在前线 1 天 | 耗粮 900，净亏 746 |
| 6 万驻军 + 粮 200 | 60 天内粮耗尽，民心跌破 50 |
| 税率 0.1 → 0.25 | 金收入 ×2.5，粮产 -7.5%，民心每日 -1 |
| 据点 1→5 级 | 粮产 ×1.6，金收入 ×1.8，驻军上限 ×5 |

**当前平衡的判断**：粮的压力已经成立，但**金的压力偏弱**（800 初始金 + 每日 11 金，几乎不会用尽）。下一步需要给"装备采购"或"赏赐"设计金的消耗出口，否则金币这个维度是死的。
