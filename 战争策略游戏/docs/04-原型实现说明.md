## 五、实现中发现的真实设计缺口

这些不是实现 bug，是设计本身的漏洞。测试过程中暴露出来，已用测试锁定当前行为。

### 缺口 1：地形只影响攻方，不影响守方

**当前规则**：地形系数按**攻方**所在位置计算。

```
伤害 = 攻方有效战斗力(攻方所在地形) × 兵种系数 × 命中率 × 守方减伤(不含地形)
```

**问题**：守方站在山地上得不到任何防御加成。**"抢占高地"这个战术在当前模型里不成立。**

**实测证据**（`battle.test.ts`的「已知设计缺口」测试）：弓兵对弓兵，蓝方在山地 vs 平原：
- 蓝方输出被扣减 → 红方受伤更少 ✓（攻方地形生效）
- 蓝方受到的伤亡**完全相同** ✗（守方地形未生效）

**是否要改**：需要改。这会让"占高地"成为有效战术，增加一层决策。但改动会使已验证的 218项跨语言一致性全部作废，需同步更新 Python 版并重新调平。

**锁定方式**：`battle.test.ts` 中有专门的测试注释说明"若未来改为地形同时影响攻方与守方，此测试会失败，届时必须同步更新 Python 版"。

### 缺口 2：编制规模小于 200 人时用 LOD0，超过 900 人时 LOD1 截断

`army.ts` 中 `MAX_INSTANCES_L1 = 900`，意味着一个 3000 人的编制会渲染成 900 个 LOD1 + 2100 个 LOD2 立方体。**视觉上会看到同一个编制里"一半精细一半方块"**。

**是否要改**：原型期可接受（俯视视角下方块阵列本身就够看）。需要改成按距离动态切换 LOD 而非按编制规模静态分配。

### 缺口 3：兵种模型 LOD0 面数超出初版预算

初版预算写 300~500 面，实测 670~708 面。**决定改预算不改模型**——砍模型要砍盾牌凸饰、头盔护鼻、马具等辨识度部件，而纯系统驱动准则下没有头顶图标，兵种全靠造型区分，砍造型换来的性能收益为零。

### 缺口 4：渲染依赖 WebGL，无降级路径（已修）

**这是用户实际遇到的故障**：预览面板里只有 HUD 面板可见，战场区域全黑。

**两个独立原因**：

1. **相机从未设置初始 position**。Three.js 相机的默认值是 `(0,0,0)`，而 `camTarget` 初始也是 `(0,0,0)`——相机正好在原点上，`lookAt(0,40,0)` 看向自己脚下的点，近裁剪面 0.5 米，结果什么都看不见。**这是全黑的主因。**
2. **无 WebGL 时 Three.js 静默失败**。部分内嵌浏览器/无 GPU 环境不提供 WebGL 上下文，`WebGLRenderer` 构造后不报错但不出图。

**修法**（两条都做了）：

- `camera.position.set(0, 900, 0.001)` 显式设置初始位置
- 新增 `src/render/capability.ts` 做能力检测 + `src/render/canvas2d.ts` 提供 **Canvas 2D 软件渲染兜底**

**兜底不是阉割版**：俯视 2D 战棋视图本身就是一种合法表现。地形按高度明暗着色（高度范围 -12~148 米，明暗对比 50%），单位按兵种符号（方=步兵 / 圆=弓兵 / 三角=骑兵）与阵营颜色区分，带选中高亮、兵力条、朝向线。框选、下令移动、攻击、交战全部照常工作。**换的是渲染后端，不是玩法。**

## 五之一、渲染后端双轨制

| 后端 | 触发条件 | 表现 |
|---|---|---|
| **WebGL（3D）** | `detectWebGL()` 返回 `webgl2` 或 `webgl` | Three.js 3D 战场，双视角切换，LOD 三层 |
| **Canvas 2D（软件）** | `detectWebGL()` 返回 `null` | 俯视 2D 战棋视图，玩法完全一致 |

降级时自动：
- 顶部显示橙色警告条说明原因与浏览器 UA
- 隐藏 3D 专属操作（WASD 平移、滚轮缩放、V 切视角按钮）
- HUD 与面板下移避开警告条

**实现位置**：
- `src/render/capability.ts` —— WebGL 能力探测（webgl2 → webgl → null 三级回退）
- `src/render/canvas2d.ts` —— Canvas 2D 渲染器（地形预渲染到 512×512 离屏 canvas，每帧只重画单位）
- `src/main.ts` —— `renderMode` 分流点，`syncUnits()` 统一收敛渲染调用

**软件渲染下的交互差异**：

| 操作 | WebGL | Canvas 2D |
|---|---|---|
| 框选 | 屏幕矩形 vs 单位投影 | 屏幕矩形 → 世界矩形直接相交 |
| 右键移动 | 射线打地形求交点 | 屏幕→世界线性变换 |
| 相机平移/缩放 | WASD +滚轮 | 不支持（固定俯视），已隐藏提示 |

**测试**：`tests/render-fallback.test.ts`（18 项）验证坐标变换可逆、框选判定、颜色解析、地形采样有效性。这组测试的价值是防止全黑屏静默回归。

**地形分布实测**（512×512 采样）：平原 43.8%、林地 18.8%、山地 28.8%、河谷 8.6%、城池 0%（地形生成器当前不产出城池）。

## 九、操控层的设计要点

### 移动模型

```
每步位移 = 速度 × 地形通行系数 × dt
朝向 = 向目标方向平滑转向（4 弧度/秒）
到达判定：位移后距目标 < 1 米则清空目标
```

**不做路径寻径**：当前直线移动。这是刻意的取舍——寻径（A*）在原型阶段收益低（地图是开阔地形，大部分路径可直线），但会显著增加复杂度。

**抵达判定的位置很关键**：必须在计算位移**之前**判断剩余距离，否则单步位移大于剩余距离时会越过目标点且目标永不清空（这是测试实跑抓到的真实缺陷）。

### 框选实现

用屏幕空间矩形 vs 单位的世界坐标投影（`THREE.Vector3.project(camera)`）。相机后方的点返回 `null` 不参与选中。

**为什么不用射线拾取单个单位**：战争策略需要"拖一个框选中一片"，这是 RTS 的标准交互。单击（矩形 < 5px）则清空选择。

### 编队形状保持

整队移动是**平移**而非"全部移到同一点"：每个单位的目标 = 当前位置 + (目标点 - 当前质心)。这样选中三支部队一起移动，它们的相对阵型不变。

## 十一、交付方式：单文件 HTML（重要）

### 为什么不用本地服务器

**本机 bash 工具无法维持长驻服务进程。** 实测：

- `nohup ... &` 启动后 HTTP 200，几分钟后变502
- `run_in_background: true` 启动后同样在数分钟内被回收

所以「启动本地服务器给你看」这个方式在本机**不可靠**，已放弃。

### 交付物

**`E:\战争策略游戏\战争策略游戏原型.html`**（543 KB，单文件）

双击即可打开，**不需要服务器、不需要联网**。所有代码（three.js 548 KB 全部内联）打进一个 HTML。

### 构建方式

```bash
cd E:\战争策略游戏
node node_modules/vite/bin/vite.js build   # 产出 dist/standalone.html + dist/app.js
node build_single.mjs                      # 合并为单文件并清理 dist
```

`build_single.mjs` 负责把 JS 与 CSS 内联进 HTML，并校验「无残留外链 JS」。

### 验证方式（无浏览器条件下的最强手段）

`tests/standalone.test.ts`（11 项）+ `tests/standalone-exec.test.ts`（9 项）：

| 验证项 | 方法 |
|---|---|
| 无外链 JS/CSS | 正则匹配产物 HTML |
| 内联 JS 语法有效 | `new Function(src)` 解析 |
| 无 import 残留 | 正则检查裸 import 语句 |
| **相机初值正确** | 严格匹配 `.position.set(x, y, z)`，要求 y 在 100~5000 |
| **无 `set(0,0,0)`** | 若存在则全黑屏（实测缺陷） |
| 兜底逻辑存在 | 匹配 `getContext("webgl2")`、`getContext("2d")`、`createImageData` |

**这组测试曾抓到假阳性**：早期版本用宽松正则匹配相机初值，实际匹配到了 `(0, 1.62, ...)` 这样的无关调用，差点给出「相机已修复」的错误结论。现已改为严格匹配，并同时断言「不存在 set(0,0,0)」。

### 能力边界（必须说清）

**这套验证能保证**：代码能跑、模块加载不报错、相机初始化正确、兜底分支存在。

**这套验证不能保证**：画面是否好看、帧率多少、交互手感如何。**这三点只有用户双击打开才能确认。**

「无法用浏览器自动化验证」是持续的缺口。Node 模拟 DOM 只能验证到「不崩」，验证不了「画面对」。
