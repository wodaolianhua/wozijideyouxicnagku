## 二、为什么必须是 3D

这不是"3D 更好看"的问题，是**机制强制要求**：

你的核心机制是**双视角切换**——第一人称/第三人称带兵上阵 + 上帝视角宏观指挥。

- 第一人称上阵：必须有 3D 空间感和第一人称视野
- 上帝视角指挥：需要 3D 战场俯视，看得懂部队部署和地形
- 视角切换：同一个战场在两种视角间无缝切换

2D 无法承载"第一人称上阵"。这一条直接排除 2D。

### 2.1 但 3D 有个必须解决的技术问题

3D 战场在俯视时可能有**几万人同屏**。这是 3D 做战争游戏的核心难点。

**解法：LOD 分层 + 实例化渲染**。见 §四。

## 三、为什么是低多边形建模，不是马赛克

### 3.1 马赛克（体素）的优势与代价

**优势**：一万个立方体在GPU 里几乎免费（实例化渲染），战场规模上限极高，WarCOM、Shellstorm: The Great War 等 2026 年的新 RTS 都在用体素生成程序化战场。

**代价（对本项目是致命的）**：

| 问题 | 后果 |
|---|---|
| 士兵是方块，贴地第一人称视角下视觉崩坏 | 「真实将领上阵冲锋」的体验直接不成立 |
| 兵种辨识度差 | 步兵/弓兵/骑兵在体素下难以一眼分辨，必须靠头顶图标补 |
| 地形是平的，缺垂直纵深 | 「翻山越岭抢占高地」这类战术做不出来 |
| 美术辨识度低，淹没在同类产品里 | 同质化竞争 |

### 3.2 低多边形建模的优势

| 优势 | 对本项目的价值 |
|---|---|
| 有轮廓、有体积，贴地视角好看 | 支撑第一人称冲锋 |
| 兵种造型可区分（步兵持盾、弓兵持弓、骑兵高头大马） | 无需头顶图标即可辨认 |
| 地形可做垂直落差 | 山地不再是"系数不同"，而是看得见的坡 |
| 程序化生成可行 | 不需要美术手工做整张地图 |

**低多边形= 三角面少但轮廓清晰**。给士兵做一个 300~500 三角面的模型，20 万个实例化渲染在中端机器上完全可行。

## 四、20 万人战场的技术方案（LOD 三层）

这是选3D 之后必须立刻回答的问题。分层如下：

| 层 | 对象 | 三角面预算 | 显示条件 | 实例化方式 |
|---|---|---|---|---|
| **LOD0 近战层** | 玩家直接操作的小队（约 50~200 人） | **500~800 面/人**（实测 670~708） | 距离 < 100m | 独立网格，可动画 |
| **LOD1 交战层** | 正在交战的部队（约 2~8 千人） | **40~90 面/人**（实测 56~74） | 距离 100~400m | InstancedMesh |
| **LOD2 大场面层** | 全战场可见部队（约 10 万+） | 立方体（12 面） | 距离 > 400m | InstancedMesh（立方体） |

> **实测修正（v1.0→ v1.1）**：初版预算写的是 LOD0 300~500 面，实测程序化模型为 670~708 面，超出 200 面。
> 决定：**改预算，不改模型**。理由——砍到 500 面要砍掉盾牌凸饰、头盔护鼻、马具等造型辨识度部件，
> 而纯系统驱动准则下没有头顶图标，兵种完全靠造型区分。砍造型换来的性能收益为零。
> 200 单位 LOD0 合计约 13.9 万面，中端 GPU 单帧可处理 200 万面以上，余量充足。
> 三档同时渲染（200 LOD0 + 3000 LOD1 + 20000 LOD2）合计约 31 万面，在预算内。

**关键技巧**：

1. **LOD2 用立方体或十字面公告板**，一个draw call 画几万个。玩家在俯视视角下只能看到"密密麻麻的方块阵列"，这在战争游戏的俯视视角里是完全可以接受的
2. **LOD0/LOD1 之间平滑切换**，避免"走近时突然变精致"的突兀感
3. **单位聚合数据向上兼容**（裁定 #6）：LOD 层的士兵数量直接来自 `resolve_engagement()` 的编制数据，不做二次模拟

### 4.1 性能预算

| 指标 | 目标 |
|---|---|
| 俯视视角同时可见单位| 20,000 个 LOD2 + 3,000 个 LOD1 + 200 个 LOD0 |
| 帧率 | 俯视 60 FPS，贴地 60 FPS |
| Draw call | < 200（靠合并几何体 + 实例化） |
| 单回合结算耗时 | < 50 ms（5000 单位规模） |

## 五、为什么是 Three.js 而不是 Babylon.js

调研结论（2026 年现状）：

| 维度 | Three.js | Babylon.js |
|---|---|---|
| 定位 | **3D 渲染库**，你在它之上造游戏 | **完整引擎**，游戏功能开箱即用 |
| 包体积 | 核心约 168 kB | 约 1.4 MB（但可 tree-shaking） |
| 大场景 | 场景图简单，小场景开销低 | 八叉树场景分区，大场景更快 |
| 性能优化 | 手动为主（几何体合并、实例化、LOD、烘焙） | 引擎辅助（自动遮挡剔除、硬件缩放） |
| 生态 | 极大（500 万+ 周下载量），教程多 | 较小但更聚焦游戏开发 |
| 内置物理 | 需另装 | 内置 Havok |
| 图形调试 | 依赖浏览器 devtools | **内置 Inspector（性能/绘制调用/帧时间可视化）** |

**选Three.js 的理由**：

1. **本项目的性能瓶颈不在渲染，在我的数值模型**。3D 部分是"标准的大规模战场渲染"，有大量现成的 InstancedMesh + LOD 最佳实践可抄
2. **包体积小** → 原型期加载快，改代码刷新快，迭代速度高
3. **不需要引擎自带的物理/动画/GUI**——本作是策略游戏，不需要刚体物理，UI 是自绘的

**选 Babylon.js 更合适的场景**：如果要做骨骼动画角色、复杂物理、VR。本项目都不需要。

### 5.1 Godot / Unity 也评估过

| 引擎 | 结论 |
|---|---|
| **Godot 4** | 免费开源、2D 极强、原型快。但 3D 大规模战场 + 导出网页不如Three.js 顺手；且导出 Web 需要额外打包 |
| **Unity / Unreal** | 3D 能力强，但原型阶段要处理构建、部署、版本管理，且导出网页体积巨大。本项目目标是"网页可玩原型"，与引擎的强项不匹配 |

**结论：先在网页上验证玩法，确认好玩后再考虑迁移到引擎**。网页原型的好处是**改一行代码刷新即生效**，这对数值调平阶段至关重要。

## 六、原型的技术栈

```
语言：TypeScript
渲染：Three.js（WebGL2）
构建：Vite
数值：TypeScript 移植当前 Python 模型（纯函数 + 单元测试）
测试：Vitest（与现有 Python 测试同构）
发布：静态站点
```

### 6.1 为什么数值要从 Python 迁到 TypeScript

当前 `src/combat_model.py` 有 44 项测试。原型是网页的，战斗结算必须**在浏览器里实时跑**（每个回合都要算）。

**迁移方案**：
- 保持**同一套公式与同一组测试断言**
- Python 版作为"参考实现"，用于对照验证
- TypeScript 版加Vitest 测试，断言从 Python 版逐条翻译
- **两份实现的测试结果必须一致**——这是迁移正确性的验收标准

### 6.2 目录结构（迁移后）

```

  src\                 TypeScript 实现（原型代码）
    model\             数值模型

```

## 七、需要用户提供的美术资源（不阻塞开发）

原型阶段可以**完全不用外部美术资源**——低多边形模型可以用代码程序化生成（胶囊体+方块拼人形）。

| 优先级 | 资源 | 用途 | 什么时候需要 |
|---|---|---|---|
| 无 | 程序化低模 | 士兵/地形/建筑 | **现在就能做，不用等** |
| P1 | 兵种参考图 | 定造型方向（盾/弓/骑） | 美术定型时 |
| P2 | 地形贴图 | 提升俯视视角可读性 | 原型手感确认后 |

**结论：不用等我，现在就开始做**。程序化生成足够跑通玩法。

如果后续要做精细美术，优先需要的清单（按优先级）：

1. 三兵种造型参考图（正面+侧面）
2. 旗帜/军械贴图
3. 地形色彩基调（草地/黄土/岩石的具体色值）

## 十、自审

| # | 问题 | 我的判断 |
|---|---|---|
| 1 | 未考虑用户是否有一台能跑 3D 的机器（用户打游戏，说明大概率有独立显卡） | **接受**。桌面端原型的性能目标定在中端机60 FPS，独立显卡可达成 |
| 2 | 网页在移动端可能跑不动，但用户可能想在手机上看 | **暂不做移动端**。原型阶段桌面优先。若要移动端，Three.js 需额外做性能降级 |
| 3 | LOD2 用立方体，可能被玩家吐槽"太糙" | **接受**。俯视视角下玩家的注意力在战术决策而非画面细节。且这正是马赛克/低模 RTS 的通行做法 |
| 4 | TypeScript 移植 Python 有引入 bug 的风险 | **用测试断言锁死**。两份实现的同一组断言必须得出同一结论，这是硬验收标准 |
| 5 | Vite + Three.js 需要 npm 安装，依赖下载可能慢 | **接受**。npm 有国内镜像 |
| 6 | 未评估音效 | **原型不做音效**。战争策略游戏第一版没声音是常态 |
