## 五、这套文档到底是什么（性质界定）

用户此前询问"这到底是不是那个游戏的选项剧情文档"，明确界定如下：

### 是的，它是"玩家选项 → 后果 → 剧情"的游戏设计文档

具体对应关系：

| 文档 | 在游戏中对应什么 |

### 但它**不是**可运行代码

### 8.2 与设计文档的一致性

**本次升级未新增、未修改任何设计命题。** 三条对应关系可核对：

1. 地图配色跟政体走（铁血红 / 融合紫），依据《12》的连续属性派生——`iron = 禁忌×0.5 + 战争伦理×(-0.3) + 排外传统×30`，是既有公式的实现，不是新设计。

### 8.3 视觉引擎的四个可测判据

本轮所有调色**不靠目测**，全部依据实测阈值。这四条已写死为自动化断言：

| 判据 | 阈值 | 由来 |
| :--- | :--- | :--- |
| 海陆相对亮度差 | > 22% | 实测 5/10 个时代达不到，画出来是一整片糊掉的棕灰 |
| 海陆绝对亮度差 | ≥ 24 | 相对差达标但两者都很暗时，画面仍是一团黑 |
| 海岸线描边遍数 | ≥ 3（辉光/主线/浪花） | 《05》视觉节第一条 |
| 中立政体岸线明度 | 不得三分量全高 | 浅羊皮色混白后会成刺眼白边 |

> **本轮最关键的一条技术教训**：海陆亮度必须**按 `drawMap` 的真实混色路径取值**——
> `mix(ground[0], ground[1], t*0.8)`。早前测试取 `Math.max(...ground)`，算出来的是数组里最亮那一档，
> 而屏幕上最亮的水格是 `t≈1` 时的混色，两者不是一回事，导致调色完全无依据、反复返工。

### 8.4 一次严重事故：196 项断言全绿但浏览器黑屏

迷雾渐变误写成 `'rgba(' + mist.slice(1) + ',' + alpha + ')'`——`slice(1)` 去掉的是 `#`，
拼出 `"rgba(110c0a,0.210)"`，真实浏览器抛 `SyntaxError`，**整幅地图一笔都画不出来**。
而当时 **196 项 Node 断言全部通过**。

根因：测试替身的 `addColorStop` 是个空函数。已改为真校验颜色格式，并用注入回溯验证
（新断言确实报出 30 处不可解析色）后恢复。

**结论已写入 README 第一节纪律：Node 全绿 ≠ 浏览器能跑。测试替身越"宽容"，越等于没有替身。**
后续任何涉及 Canvas / DOM / 浏览器 API 的改动，都必须在真实浏览器复验。

### 8.5b 第二轮修复：10 类观感缺陷（同源教训）

可视化版首次交付后，在真实浏览器截图审计中又发现 10 处观感问题。
**它们的共同根因是同一条纪律被违反了第二次**：已有断言测的量与人在乎的量不是同一个。

最典型的一例：截图里海岸线几乎看不见，但已有断言写的是"描边遍数 ≥ 3"——
那是**画了几次**，不是**看不看得见**。用对照实验（同种子同状态，`reveal=1` 与 `reveal=0`
各画一张）证明：关雾时大陆外缘那圈亮线完整连贯，开雾时几乎被吞平，
根因是雾的外圈 alpha 到了 0.90，而海岸线恰恰画在大陆外缘——正好是雾最厚的地方。
封顶 0.62 后，实测亮线保留率从 ≈0% 升到 **77%**。

| # | 缺陷 | 观测到的现象 | 修法 |
| :--- | :--- | :--- | :--- |
| 1 | 迷雾外圈 alpha 0.90 | 海岸线被整条吞掉 | 封顶 0.62，保留率 0% → 77% |
| 2 | 山峰 = 暗块 + 亮竖条 | 焦黑 T 形，像烧焦的树枝 | 三层阶梯山（暗体/背光面/受光面 + 雪顶） |
| 3 | 山峰提亮量固定 +0.32 | 羊皮纸陆相 L=200，只能提到 218（+8.9%） | `litK` 随底色自适应，达不到 12% 就加码 |
| 4 | 受光面随层宽等比收窄 | 顶层算出 1.2px，亚像素等于没画 | 设 2px 绝对下限 |
| 5 | 抽样基数用画布格数 | 羊皮纸时代受光面亮像素只剩 3 个 | 改用「该类地形格数」 |
| 6 | 抽样系数 0.055 | 时代 1 只有 2~3 座山 | 提到 0.16 + 下限 6 座 |
| 7 | 河色提亮 0.26 | 放大后是近白宽带，亮度盖过海岸线 | 降到 0.16 |
| 8 | 地标无基座 | 纯色方块浮在陆面上，像彩色纸屑 | 加暗基座（陆相压暗） |
| 9 | 地标密度偏高 + 基座过黑 | 满地橙点抢戏，喧宾夺主 | 数量降档，基座压淡 |
| 10 | 结局页地图 3:1 | 方形地形被压成扁块 | `aspect-ratio:1.85/1` |

**沉淀为项目纪律**（已写入《可玩原型/README.md》第二节）：

> **断言必须测真正关心的那个量。**
> "描边遍数" ≠ "看得见"；"亮度分层数" ≠ "有立体感"；"JSON 里有这个字段" ≠ "玩起来有这个东西"。
> **推论**：新加断言必须做**注入回溯**——把 bug 改回去，确认它报警。
> 没验证过的断言，很可能只是个安慰剂。

### 8.5c 关于"给视觉缺陷写断言"的一条反向教训

山峰那条断言换了**四版**才站住，四次都是想用「像素统计」代理「形状是否可读」：
全图亮度分层（噪声淹信号，注入回退仍全绿）→ 绝对阈值（明亮时代误报）→
以 `A.land` 为基准（底砖早被政体染色）→ 以陆面中位为基准卡倍率
（羊皮纸时代受光面**物理上限只有 1.197 倍**，卡 1.18 只剩 3 个像素过线，放宽又对噪声放行）。

最后改成数「符号层用了几档明度」——这是**定义本身**而非代理指标。

**结论：判据本身也要评估价值。** 为一个低频风险建一条需要四轮才能稳定的
像素统计断言是**负收益**——真要防"有人把三层改回两层"，靠的是代码评审 + 注入回溯。
这条已写入 README，避免后来者重复投入。
