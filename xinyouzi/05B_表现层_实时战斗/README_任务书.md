## 为什么延后

实时战斗会撑破骨架。这是整个项目最大的架构风险，必须讲清楚：

如果战斗是**实时且不可打断**的，它就无法被 `Tick` 推进，也就无法与 `Order → Resolver → WorldState` 这条主干集成。结果会是**两套独立系统**：策略层一套、战斗层一套，中间靠数据转换对接。

一旦变成两套系统，会立刻出现三个无法修复的问题：

1. **状态回滚困难**——玩家战败要退回回合开始状态，两套状态难以对齐
2. **无头模拟失效**——平衡验证跑不了，因为批量模拟不能等实时战斗打完
3. **存档复杂度爆炸**——战局中途存档要同时序列化两套状态

## 集成方案（启动时遵循）

实时战斗**不替代**回合制结算，而是作为一种特殊指令的详细表现：

```
玩家下达 Dispatch 指令
        ↓
Resolver 判断这是普通攻城还是需要实时战斗
        ↓
        ├── 普通攻城 → 回合制批量结算（原路径）
        ↓
        └── 实时战斗 → 打开战斗场景（不推进世界时间）
                    ↓
                战斗结束，产出StateDelta
                    ↓
                StateApplier 统一写回 WorldState
                    ↓
                回合继续推进
```

关键约束：

- **实时战斗期间世界时间不推进**（`Tick` 挂起）
- **战斗结果以 `StateDelta` 形式返回**，走和回合制结算**完全相同**的写回路径
- 战斗中玩家战败→ 产出负向 `StateDelta`（兵力损失），城市易手
- 战斗可撤退→ 按损失比例返还兵力，不惩罚性全损
