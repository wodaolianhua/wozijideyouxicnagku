## 三、三个设计缺陷，全部采纳

### 缺陷 A【严重】恢复与腐化同月叠加 → 连续作战完全无惩罚

03 报的是"和平腐化净变化 +1，腐化无效"。**这个描述只对了一半。**

我代入实算后发现**更严重的问题**：当前实现是「无论参战与否，先 +3 再判腐化」。
于是——

```
每 2 月一战（未决 −3）+ 每月恢复 +3 = 士气恒定 60，永不下降
```

**后果**：无脑连续攻城成了最优解（士气永远满 → 战损永远最低），
"用人/练兵/休整"的整个玩法内核被架空。

**只调数值救不回来**——即使把腐化调到 −6，只要恢复仍在参战月叠加，
连续作战照样无惩罚。必须改规则。

**定稿**（已写入 `4_数值框架.md` 5.2.1 与契约）：

| 项| 初稿 | 定稿 | 依据 |
|---|---|---|---|
| 恢复 +3/月的生效条件 | 每月都生效 | **只在未参战月生效** | 参战月恢复会抵消战斗惩罚 |
| 和平腐化 | −2 / 月 | **−6 / 月** | 必须大于恢复值，否则净变化 ≥ 0 仍是死条款 |
| 腐化阈值 | 6 个月 | **4 个月** | 一局仅 60-72 回合，阈值 6 等于永远触发不了 |

**实算验证**（三条全过）：
- 纯和平 12 月：60 → 63 → ... → 36 → 30 → **24**，跌破 30（战损 +150% 档）✓
- 每 2 月一战 + 战后轮休：稳定 57 ↔ 60，不会自己打崩 ✓
- 阈值 4 意味着"放着 4 个月不打"就要付代价 ✓

### 缺陷 B 契约缺 `RejectedTargetSieged`

**03 报得对，已补。** 契约 v1.3 变更：
- `ResolveResultCode.RejectedTargetSieged = 10`
- `ApiContract.ErrorCodes.TargetSieged = "TARGET_SIEGED"`

理由：「已被占领」是**永久**拒绝（要换目标），「被围困」是**临时**拒绝（等下个月）。
混在一个码里，玩家会以为围城是永久的，从而放弃"围城牵制"这个战术。
UI 也需要显示不同的文案。

### 缺陷 C 野战注释与实算不符

**03 报得对，文档已订正。** 但顺着查下去我做了完整验算，结论是**代码没错**：

| | 野战 | 攻城 |
|---|---|---|
| `lossRate`（均势） | 0.175 | 0.350 |
| `killRate`（均势） | 0.540 | 0.401 |
| **全歼对方所需兵力** | **约 1.85 倍** | 约 2.5 倍 |

野战 `(2 - defenseFactor)` 从 1.5 变成 2.0，所以 killRate 翻倍。
结果是**野战确实比攻城更划算**，正是这套系数想要的效果。

**但发现配置错误**：`FieldBattleLossFactor` 被填成 6000（0.6），
按 `BaseLoss × 0.6 = 0.21` 算，与我原设计的 0.5（=0.175）不符。
已在契约注释里订正为 **5000**，并在 `3_战斗系统设计.md` 3.5 节写清实算过程。

## 五、给 02 的答复（它问的两点）

**问：要不要清 `bin/` 下的旧构建产物？**
**答：不用管。** `bin/` 是构建输出，不进版本管理，`dotnet clean` 自然会清。
它不存在"污染"问题。但 `grep` 建议加 `-l` 只看文件名，或排除 `bin/ obj/`，
否则噪音大。

**问：玩家人口总和要不要最低？**
**答：不用。** 它自己改的修法是对的。
边疆势力人口少但兵力强、民生弱，是合理的不对称。
约束应该只针对玩家：**每座玩家城池的人口，低于中原霸主最大城池的人口**——
这条能防止玩家拿两座大城当本钱，同时允许边疆这种"地广人稀"的风格。
