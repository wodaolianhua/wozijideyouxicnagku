## 二、02 包报出的契约缺陷裁决

### 缺陷 1：`GrainPerPopPerMonth` / `SoldierPerPopPerMonth` 是 int，装不下小数

02 报称任务书要求 `0.08`（粮产系数）和 `0.5`（兵产系数），但契约声明为 `int`。

**裁决：02 包报对了，这是真契约缺陷。定改为万分比定点整数。**

```
GrainPerPopPerMonth      int   800    = 0.08 × 10000
SoldierPerPopPerMonthint  5000   = 0.5  × 10000
```

**但这会连带影响 03 包已实现的代码**（它现在按 `/ 100` 之类的口径算），
所以这是**契约破坏性变更**，必须走完整流程：

1. 01 包更新 `4_数值框架.md`，全文把这两个系数改为万分比表示
2. 我修改 `Interfaces.cs`
3. 跑 `bash E:/xinyouzi/分发契约.sh`
4. **03 包必须返工**（吃粮/产兵/征兵相关代码 + 测试）
5. 02 包更新 `config.json` 对应键值

**关键：不要为了"少改一个包"而把 0.08 硬塞进 int。** 那会让粮产变成 0，
整个经济系统归零。定点整数是战斗系统已经在用的做法（万分比），
经济系统跟着用同一套刻度，不是负担而是统一。

### 缺陷 2：`GameEventTemplate.Id` 是 string，与"禁用字符串 ID"冲突

02 报称这是真冲突。

**裁决：02 包报对了。改 `int`。**

理由：
- `FileOwnership` 与 `ApiContract` 都要求整数 ID，JSON 里的实体 ID 必须统一
- 字符串 ID 在跨语言（TS侧）序列化时容易变成 `string` / `number` 混合类型
- 事件表是纯配置，ID 只用于引用，没有任何需要字符串的理由

同时 `GameEventTemplate` 的 JSON 里若有 `Id` 字符串，全部改为整数，
并由02 包在校验器里加一条硬规则：**所有 `*Template` 的 ID 必须为正整数**。

### 缺陷 3：任务书里5 个字段契约中无对应项

02 报称任务书提到 `rewardCostSilver` 等字段但契约无对应。

**裁决：先不扩契约。**任务书是02 包自己的实现细则，不是跨包接口。
这些字段如果只是 02 内部读取用的配置键，应该写在 02 自己的 `ValidationResult`
模型里，**不要塞进共享契约**。共享契约只放"其他包也需要知道"的字段。

**判断标准**：03 包需要读它吗？不需要 → 不进契约。

## 三、战斗公式修正（影响 03 包，必须返工）

### 驳回 03 包的修法

03 报称："守方损失改为按「攻方投入兵力 × lossRate × 0.6」计"

**这个修法引入了新的逻辑倒错**：投入越多→ 守方损失越大 → 破城越快。
兵力优势应该体现在**能不能打下来**，不应该体现在**打下来时守军死多少**。
更严重的是，它仍然是"攻守共用一个 lossRate"，而共用一个系数必然导致
"强将降低lossRate → 守方更抗打 → 强将反而破城更慢"。

### 采用的正式方案：攻守两条独立公式

已写入 `3_战斗系统设计.md` 第 3.1 / 3.2 节，此处只列结论：

```
lossRate = 0.35 × (0.5 + 城防/1000) × (2 - 2 × commanderRatio)   # 攻方自损
killRate = 0.27 × (2 - 城防/1000) × (2 × commanderRatio)         # 守方被歼
攻方损失 = 投入 × lossRate
守方损失 = min(投入 × killRate, 守城兵力)

判定顺序：先lossRate >= 0.70 判击退，再判守方损失 >= 守军 判攻陷，都不满足判未决
```

`commanderRatio` 口径统一为 `攻 / (攻 + 守)`，**去掉 `+1`**（原 5_指令字典里的写法是错的）。

**契约新增 `BaseKill = 2700`**，标记 `DefenderLossFactor` 与 `StalemateLossRate` 为 `[Obsolete]`。
已跑 `分发契约.sh`，各包副本已同步，契约工程编译零警告零错误。

### 03 包需要做的返工

1. `BattleSystem` 重写为双公式
2. 判定顺序改为"先击退后攻陷"
3. 新增 `BaseKill` 读取；`DefenderLossFactor` / `StalemateLossRate` 不再参与计算
4. `commanderRatio` 去掉 `+1`，检查全部调用点
5. 按 `3_战斗系统设计.md` 第七节的新验收标准补测试（8 个用例，测试名已给出）

先在 `4_数值框架.md` 补一节士气系统设计，再让 03 实现。
