# 二、03 包返工

## 2.1 【核心】战斗公式改为攻守两条独立公式

你把自己发现的"守方损失逻辑不可达"修成了
`守方损失 = 攻方投入 × lossRate × 0.6`。

**方向对，但只解决了一半**——攻守仍然共用一个 `lossRate`，这会带来新的问题：
共用一个系数后，强将降低 lossRate 的同时也会降低守方损失，
结果是**强将反而破城更慢**。这是个更隐蔽的逻辑倒错。

**正式方案**（已写入 `3_战斗系统设计.md` 第 3.1/3.2 节，以那里为准）：

```
# 攻方战损率：攻方每投入 1 点兵力，自己损失多少
lossRate = 0.35 × (0.5 + 城防/1000) × (2 - 2 × commanderRatio)

# 守方被歼率：攻方每投入 1 点兵力，能打掉多少守军
killRate = 0.27 × (2 - 城防/1000) × (2 × commanderRatio)

攻方损失 = 投入 × lossRate
守方损失 = min(投入 × killRate, 守城兵力)
```

**契约字段**：`BaseLoss`= 3500，`BaseKill` = 2700。全部走配置，禁止硬编码。

**注意两个式的方向相反且都是必须的**：

| | 城防↑ | 统帅强↑ |
|---|---|---|
| `lossRate`（攻方自损） | ↑ 更亏 | ↓ 更省 |
| `killRate`（打掉守军） | ↓ 更难打 | ↑ 更快打 |

## 2.2 判定顺序：先击退，后攻陷

```
1. lossRate >= 0.70        → 击退，攻方退回原城
2. 守方损失 >= 守城兵力→ 攻陷，城易主
3. 都不是→ 未决
```

**顺序不可调换**：若先判攻陷，`lossRate` 已 ≥ 0.70 的强攻在守军恰好被打光时
会同时满足两个条件，顺序不同结果就不同。

## 2.3 攻击陷判定，排除重复扣兵

原实现里`守方损失` 和"未决双方各损 10%"重复计算了。
现在未决**按正常公式结算，不再额外扣**。`StalemateLossRate` 字段废弃。

被围困城标记 `Siege`，下月不可再对该城Dispatch，返回 `RejectedTargetSieged`。

## 2.4 `commanderRatio` 去掉 `+1`

你在汇报里问5_指令字典的 `攻/(攻+守+1)` 和 3.1 的 `攻/(攻+守)` 哪个对。

**`攻/(攻+守)` 对，`+1` 是错的。**

理由：`+1` 会在双方统帅悬殊时把比值强行拉向 0.5
（100 vs 0 时本应是 1.0，加 1 后变成 0.99；但40 vs 50 本应 0.444，
加 1 变成 0.475，被拉向 0.5），恰好抹掉"强将/弱将"的差异。

**全项目统一为 `攻 / (攻 + 守)`，两边皆 0 时取 0.5。**
检查 `BattleSystem` 全部调用点。

**① 低士气惩罚要在比较阈值之前乘上，且不得钳制**

## 2.11 一个重要的设计转向（会影响你 EconomySystem 的取舍）

早期文档写"348粮养 3.4 万人"，**这是算术错误**，实际是 1.74 万人。
我已修正 `4_数值框架.md`，这里同步告知，因为它影响你实现时的判断：

**粮不是真正的瓶颈，兵源才是。**

| 约束 | 真实压力 |
|---|---|
| 粮草 | 348 粮能养 1.74 万兵 —— 相对宽松 |
| **兵源** | 3000 人口城每月只产 **90 兵**（`3000 × 5000/10000 × Stability/100`），攒 5000 兵要 4 年 |
| **失城** | 人口归零 → 粮产 + 兵源一起腰斩 |

**含义**：压迫感不来自"饿肚子"，来自**"人不够"**和**"打下地也守不住"**。
这直接决定两件事：
1. 饥荒事件应该**很难自然触发**（要等到兵力远超产粮能力才可能），它更像是极端事件的兜底，而不是常驻机制
2. `Stability` 的重要性高于粮储——它直接乘在兵源产出上

**不要**把 EconomySystem 写成"粮不够就崩"的模型。粮耗只是支出项，
真正的瓶颈是 `SoldierPerPopPerMonth × Population × Stability`。
