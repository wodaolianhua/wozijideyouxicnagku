# 启动提示词 · 分发给执行 AI 用

> **本文件的用法**：复制某一段，粘给一个新的 AI 对话。那个 AI 只读对应的包文件夹，按提示词执行。
>
> **重要**：不要把所有提示词一次性发给一个 AI。**一个包一个对话**，
> 这样它们互不知晓对方进度，正好验证契约能不能保证组合成功。
>
> **开哪个包、按什么顺序**：见 `轮次调度.md`。

## 提示词 1：03 规则内核层（最高优先级，已做一轮需返工）

```
【任务】规则内核返工。这是整个项目的脊椎，也是本轮最重的一个包。

文件夹：E:\xinyouzi\03_规则内核层\

⚠️ 你接手的是一个已交付但需返工的工程。先读：
  E:\xinyouzi\00_项目管理\返工指令_契约v1.2.md 的「二、03 包返工」一节
里面列了全部 11 项返工内容和现成的测试名，照做。

【本轮返工重点】
1. 战斗公式改双公式：lossRate（攻方自损）+ killRate（守方被歼）
   —— 不能共用一个系数，否则会推出"强将反而破城更慢"
2. 判定顺序改为：先判击退（lossRate ≥ 7000），再判攻陷，最后未决
3. commanderRatio 去掉 +1，统一 攻/(攻+守)，两边皆 0 时取 0.5
4. 耗粮系数统一为万分比：兵力 × (ArmyMonthlyGrainPerSoldier / 10000)
5. 新增士气系统（7 个配置字段 + Army 两个新字段 + GetMoralePenalty）

【最容易出错的三个地方】
- 士气倍率必须在与阈值比较【之前】乘上 lossRate，
  且绝对不要写 Math.Min(lossRate, 1.0) —— 钳制会让士气惩罚完全失效
- Army.Morale（部队士气）与 Resources.Morale（势力民心）同名不同物，
  实现时用不同命名区分（Army 用 morale，Resources 用 popularity）
- Army 新增的两个字段必须进 Clone()，漏了会导致回放状态不一致

【硬约束 · 不要动摇】
- Resolver 必须是纯函数：只读 state，不改它，状态变化只通过 StateDelta 表达
  这不是建议，是硬约束。后面的无头模拟、回放、存档全部依赖这一点
- 随机必须走 IRandom 接口，不能用 Random.Shared / Guid.NewGuid() / DateTime.Now
- 所有系数从 BalanceConfig 读，不能硬编码
- 所有比率用万分比整数，整除截断统一向下取整，且截断方向必须有测试锁定
  （浮点取整在不同语言里结果可能不同，这是跨语言协作的隐患）

【必须通过的测试】
- Clone 深拷贝测试（含新增的 morale 相关字段）
- 确定性测试：同 Seed 跑两次，最终状态逐字段相等
- 纯净性测试：Resolve 调用前后 state 未变
- 战斗：8 个场景测试（返工指令里已给出测试名和期望值）
- 士气：11 个场景测试（返工指令里已给出测试名和期望值）
- 每个 Resolver 的成功路径 + 至少一条拒绝路径

【验收】
dotnet build 零错误零警告，dotnet test 全部通过。
汇报构建和测试的实际输出。
```

## 提示词 3：04 智能体层（等 03 完成后再开）

```
【任务】实现 AI 势力决策与人才系统。

文件夹：E:\xinyouzi\04_智能体层\

前置：03 包必须已经完成且能编译。你需要引用 StrategyGame.Core。
如果 03 还没完成，先停下来问，不要自己造一个假的 03。

⚠️ 有两条 03 已定稿的语义变更，直接影响你写AI，必须按新语义实现：
  1. 出兵到【自家城池】不再走战斗系统 —— AI 不会"攻打自己的城"，
     这条路径直接进Dispatch 常规流程
  2. RejectedTargetOccupied 语义收窄 —— 从"目标已被占领"改为
     "目标已被围困（Siege）"。真正的占领由攻陷结果体现，不是这个错误码

核心要求：
1. 实现 IFactionPlanner（AI 势力决策）
2. 实现 IPersonnelPolicy（人才政策）
3. 实现忠诚度系统与赏赐反制机制

【最关键的验收项】
换人之后结算结果必须【可观测地变化】。
具体测试：把 Agriculture 专长的人才放到城守岗，粮产明显提升；
换成一个 None 特质的，粮产回落。如果数值不变，"用人"就是装饰，测试失败。

【AI 必须会做的事 · 这是本包的灵魂】
- 评估威胁：哪座城被打的风险最高，优先派兵守
- 认清兵源是瓶颈：3 座城才有 270 兵源/月，攒兵比守城更急迫
  （注意：粮不是瓶颈，348 粮能养 1.74 万兵。压迫感来自"人不够"和"守不住"）
- 会休整：连续打仗的部队士气会掉（击退 -12），士气 20 以下会从攻陷翻成击退
  AI 应该在士气崩之前主动 Rest，而不是无脑连续进攻
- 会换人：统帅平庸时换更强的上去，这才是"用人"玩法的AI 侧验证

【铁律】
AI 只能产出 Order，禁止直接修改 WorldState。
审查时看到任何对 state 的写入，一律打回。
理由：AI 走了一条玩家走不通的路径时，平衡验证会全部失效。

【必须通过的测试】
- 连续模拟 100 回合不崩溃、不产生非法 Order
- 单次 Plan 耗时 < 5ms
- 忠诚度有升有降，不存在只降不升的单向路径
- AI 在兵源不足时不会无脑扩张（打不起就该屯田）
- AI 会用 Rest 恢复士气，不是永远进攻

【不要做】
不要实现 P1/P2 内容（人才招揽、赏赐指令的完整实现），
那些在契约里已经保留了 ActionType 编号但标注了阶段。
```

## 提示词 4：06 工程与验证层（等 03 完成后再开）

```
【任务】建立存档、回放、无头批量模拟器。

文件夹：E:\xinyouzi\06_工程与验证层\

前置：03 包必须已完成。

核心要求：
1. SaveSystem —— JSON 格式，必须包含 Seed
2. ReplaySystem —— 回放结果必须与原始模拟逐字段相等
3. BatchSimulator —— 无头批量模拟，这是项目最有价值的工程资产
4. 命令行工具 + CSV 导出

【为什么这个包优先级高】
它决定项目的迭代速度。改一次数值要重新编译、手动点20分钟 UI，
设计师就不敢改数值。有了这个，改 JSON → 跑 1000 局 → 对比报告，
调平衡才有意义。

【必须通过的测试】
- 确定性测试：同 Seed 两次模拟最终状态完全相等
- 回放测试：Replay 结果与原始模拟一致
- 1000 局 120 月，4 核 5 分钟内跑完

【平衡性判断标准，写进报告】
- 玩家胜率（vs 2 AI）应在 25%-45%。太高说明 AI 太弱，太低说明平衡有问题
- 平均存活回合 ≥ 60。太低说明玩家容易早期被灭
- 首回合终局比例接近 0

【第二轮模拟要额外看的指标 —— 这是调平衡的真正抓手】
- 平均兵源存量：AI 是否在攒兵？如果 AI 常年满编扩张，说明兵源压力不够
- 士气分布：AI 的部队士气长期低于 30，说明它在无脑连续作战，
  AI 的 Rest 逻辑可能没生效
- 攻陷次数 / 尝试次数：正常应 30%-50%。过低说明大家都打不下来，
  过高说明战斗公式太宽松
- 僵持率（未决占比）：正常 20%-40%。过高说明胜负判定太模糊

【注意】
这个包里发现问题不要自己改 StrategyGame.Core 的代码——
那是 03 包 owner 的文件，写变更申请。
也不要自己调 BalanceConfig 的数值来"改善"报表数字，
那是设计层的决定。**报告里如实写数字，让数据说话。**
```

## 开几个对话、什么顺序

**完整的轮次路线图见 `轮次调度.md`。** 当前状态：

```
现在开（第 2 轮，返工）：
  提示词 1（03 规则内核返工）  ← 最重，占大部分时间
  提示词 2（02 内容数据返工）  ← 与 1 并行，互不依赖

第 2 轮收工后开：
  提示词 3（04 智能体）
  提示词 4（06 工程验证 · 无头模拟器）

第 3 轮收工后开：
  提示词 5（05A 表现层）        ← 做完这轮你就能亲手玩

05B 实时战斗：暂不开，玩法验证通过后再启动
```

**关键**：即使有依赖关系，也不要让同一个对话同时做两个包。
**故意分开，才能验证契约是不是真的有效。**

如果 03 完成了但 04 编译不过、或者 05A 连不上后端——那正是契约体系的检验时刻，
把错误信息发回来，我来判断是契约缺失还是实现偏差。
