# 启动提示词 · 分发给执行 AI 用

> **本文件的用法**：复制某一段，粘给一个新的AI 对话。那个 AI 只读对应的包文件夹，按提示词执行。
>
> **重要**：不要把所有提示词一次性发给一个 AI。**一个包一个对话**，这样它们互不知晓对方进度，正好验证契约能不能保证组合成功。

---

## 通用前缀（每段都要包含）

```
你现在负责一个独立的开发包。

【第一步】只读这个文件夹里的两个文件，别的都不要读：
  1. README_任务书.md —— 做什么、边界在哪、怎么验收
  2. 接口契约_共享类型/ —— 类型定义（Enums.cs / Models.cs / Interfaces.cs）
     以及 README_契约使用说明.md 里的引用方式

【硬规则】
- 只能读当前文件夹，禁止读其他包目录
- 类型只能从 StrategyGame.Contracts 引用，禁止手抄或重新声明
- 契约文件是只读的，禁止修改
- 有疑问不要猜，去看契约文件确认

【汇报格式】每完成一个交付物，汇报：
  做了什么 / 验证方式 / 构建结果（dotnet build 输出）/ 未完成项
```

## 提示词 1：03 规则内核层（最高优先级，建议先开这个）

```
【任务】实现规则内核。这是整个项目的脊椎。

文件夹：E:\xinyouzi\03_规则内核层\

核心要求：
1. 建 C# 工程 StrategyGame.Core（.NET 8），引用 StrategyGame.Contracts
2. 实现 WorldState / Order / StateApplier / GameClock
3. 实现 6 个 Resolver 的骨架（Recruit / Fortify / Develop / Dispatch / AssignPost / Rest）
   ——骨架 = 完整的校验分支 + 正确的返回码，数值公式先用占位常量
4. 实现 TurnPipeline 的 11 步调度结构
5. 实现 ConfigLoader + ConfigValidator
6. 写单元测试

【最容易出错的地方】
- Resolver 必须是纯函数：只读 state，不改它，状态变化只通过 StateDelta 表达
- 这不是建议，是硬约束。后面的无头模拟、回放、存档全部依赖这一点
- 随机必须走 IRandom 接口，不能用 Random.Shared
- 数值系数从 BalanceConfig 读，不能硬编码

【必须通过的测试】
- Clone 深拷贝测试
- 确定性测试：同 Seed 跑两次，最终状态逐字段相等
- 纯净性测试：Resolve 调用前后 state 未变
- 每个 Resolver 的成功路径 + 至少一条拒绝路径

【设计未定稿的部分】
战斗公式、数值系数还没定（01 包在写）。用占位常量即可，
在代码里标记 // TODO(设计): 待数值框架定稿后替换
不要自己发明数值。

【验收】
dotnet build 零错误零警告，dotnet test 全部通过。
汇报构建和测试的实际输出。
```

```
文件夹：E:\xinyouzi\02_内容数据层\

   events.json / specialties.json（+ 按需增补）
2. 实现 IConfigLoader 的 JSON 实现
3. 实现 ConfigValidator——校验失败必须报错，不能静默用默认值蒙混
4. 写单元测试

【关键约束】
- 数值全部来自 01 设计规格层的设计，但那份还没定稿。
  → 用占位数值，全部标记 TODO，但【结构和校验逻辑必须完整】
- 城池的 AdjacentCityIds 必须对称（A 含 B 则 B 含 A），这是校验项
- 每个势力必须恰好一座 IsCapital，这也是校验项
- 事件的 Probability 同类别之和不得超过 60，这也是校验项
- JSON 里所有数值要有 _comment 说明用途
- 禁用字符串 ID，禁用浮点数存资源

【特别注意】
玩家是"没落贵族"，所以 officers.json 里的初始人才必须明显偏弱
（Command/Governance 40-55 区间），这是玩法设计要求，不是随便填。
另外城池要 6 座分属 3 个势力，玩家势力只有 1 座小城。

【验收】
故意写坏数据（负数、概率 101、指向不存在的城），
校验器必须能检出并给出可读错误信息。
dotnet build + dotnet test 零错误。
```

## 提示词 3：04 智能体层（等 03 完成后再开）

```
【任务】实现 AI 势力决策与人才系统。

文件夹：E:\xinyouzi\04_智能体层\

前置：03 包必须已经完成且能编译。你需要引用 StrategyGame.Core。
如果 03 还没完成，先停下来问，不要自己造一个假的 03。

核心要求：
1. 实现 IFactionPlanner（AI 势力决策）
2. 实现 IPersonnelPolicy（人才政策）
3. 实现忠诚度系统与赏赐反制机制

【最关键的验收项】
换人之后结算结果必须【可观测地变化】。
具体测试：把 Agriculture 专长的人才放到城守岗，粮产明显提升；
换成一个 None 特质的，粮产回落。如果数值不变，"用人"就是装饰，测试失败。

【铁律】
AI 只能产出 Order，禁止直接修改 WorldState。
审查时看到任何对 state 的写入，一律打回。
理由：AI 走了一条玩家走不通的路径时，平衡验证会全部失效。

【必须通过的测试】
- 连续模拟 100 回合不崩溃、不产生非法 Order
- 单次 Plan 耗时 < 5ms
- 忠诚度有升有降，不存在只降不升的单向路径

【不要做】
不要实现 P1/P2 内容（人才招揽、赏赐指令的完整实现），
那些在契约里已经保留了 ActionType 编号但标注了阶段。
```

## 提示词 4：06 工程与验证层（等 03 完成后再开）

```
【任务】建立存档、回放、无头批量模拟器。

文件夹：E:\xinyouzi\06_工程与验证层\

前置：03 包必须已完成。

核心要求：
1. SaveSystem —— JSON 格式，必须包含 Seed
2. ReplaySystem —— 回放结果必须与原始模拟逐字段相等
3. BatchSimulator —— 无头批量模拟，这是项目最有价值的工程资产
4. 命令行工具 + CSV 导出

【为什么这个包优先级高】
它决定项目的迭代速度。改一次数值要重新编译、手动点20分钟 UI，
设计师就不敢改数值。有了这个，改 JSON → 跑 1000 局 → 对比报告，
调平衡才有意义。

【必须通过的测试】
- 确定性测试：同 Seed 两次模拟最终状态完全相等
- 回放测试：Replay 结果与原始模拟一致
- 1000 局 120 月，4 核 5 分钟内跑完

【平衡性判断标准，写进报告】
- 玩家胜率（vs 2 AI）应在 25%-45%。太高说明 AI 太弱，太低说明平衡有问题
- 平均存活回合 ≥ 60。太低说明玩家容易早期被灭
- 首回合终局比例接近 0

【注意】
这个包里发现问题不要自己改 StrategyGame.Core 的代码——
那是03 包 owner 的文件，写变更申请。
```

## 开几个对话、什么顺序

```
现在就能开：提示词 1（03 规则内核）
              提示词 2（02 内容数据）—— 与 1 并行

等 03 完成后开：提示词 3（04 智能体）
                  提示词 4（06 工程验证）
                  提示词 5（05A 表现层）

05B 实时战斗：暂不开，玩法验证通过后再启动
```

**关键**：1 和 3 虽然有依赖关系，但不要让同一个对话同时做。**故意分开的，才能验证契约是不是真的有效。**

如果 03 完成了但 04 编译不过、或者 05A 连不上后端——那正是契约体系的检验时刻，把错误信息发回来，我来判断是契约缺失还是实现偏差。
