## 1. 驳回原因（00 裁决，与你包相关的 A/B 两条，原文内联）

> **A. Reward 指令是 P1 保留位，你却在发（非法指令）**
> - 契约 `ActionType.Reward = 101`，注释原文「人才获取（P1，骨架阶段不实现，保留位）」。
> - 结算端注册表只有 0-5 六个 [Proto] 行动；未注册行动一律返回 `RejectedNotImplemented`。
> - `AiFactionPlanner.AddLoyaltyOrders` 对忠诚<50 者每条都发 Reward，还有测试把这个错误行为锁死。
> - 模拟器一旦把 AI 指令过 Resolver，必然刷 NOT_IMPLEMENTED，直接违反「无非法 Order」验收。
> - P0 **没有任何合法的忠诚上升通道**：结算端 AssignPost 不加忠诚，Reward 未实现，
>   叛离执行也未实现（结算端只有忠诚衰减）。
>
> **B. 岗位由结算端按专长强制推导，你的"选岗"是空气**
> - AssignPost 结算器**完全不读指令里的岗位意图**，按人才专长定岗：
>   Agriculture→FarmOverseer、Siege→FortifyOverseer、Cavalry→General、
>   Diplomacy→Scoutmaster、其余（None/Logistics）→CityGovernor。
> - 指令字典规定 AssignPost 的 **Amount = -1（未用）**；TargetId=人才，SecondaryTargetId=城。
>   你却把 `(int)PostType.CityGovernor` 塞进 Amount。
> - **一城一岗**（城里已有任意在岗人才即占位，第二次任命同城必被拒）。
>   你逐城"补城守"只查 CityGovernor 岗、还"给首都补 General"，必然冲突或落空。

**核心认知转变**：你无权决定岗位，岗位是结算端看专长定的。你在 P0 能做的"用人"只有两件事：
**选哪个人、放到哪座缺人的城**。选才标准是 **Governance（政务）排序**，不是你的岗位想象。

### 3.2 `src/StrategyGame.AI/AiFactionPlanner.cs`

**删除**：

- `LoyaltyCareThreshold` 常量与整个 `AddLoyaltyOrders` 方法及其在 `Plan` 中的调用
  （连带删掉对 `BaseRecruitCostSilver` 当赏赐花费的复用）。
- `AddPersonnelOrders` 末尾"找一个将军/任命到首都 General 岗"整段。

**Plan 顺序**改为两段：① 人才任命（让人才有事做，即 P0 唯一的忠诚维护）；② 策略指令。
保持每势力指令数 ≤ `MaxOrdersPerFactionPerMonth`、`PlanAll` 只处理非玩家势力。

**`AddPersonnelOrders` 重写**（裁决 3）：

1. 取本势力城池；**缺岗城** = 不存在任何
   `IsAlive && Post != PostType.None && PostCityId == 该城.Id`（且 OwnerFactionId 为本势力）
   的人才。注意是"任意岗位"，不是只查 CityGovernor。
2. 缺岗城排序：`Population` 降序、`Id` 升序（确定性，不用随机）。
3. 依次为每座缺岗城选 1 名空闲人才（存活、本势力、`Post == PostType.None`），
   通过政策层取 **Governance 最高者**（调用见 3.3，注意排除"本计划里已派出去的人"，
   同一人不得在一个 Plan 里被派到两座城——state 不会因你的规划改变，必须本地维护
   `HashSet<int> assignedIds`）。
4. 产出：`Order.CreateAiOrder(ActionType.AssignPost, factionId, officer.Id, amount: -1, secondary: city.Id)`。
5. 选不到人（空闲人才耗尽）立即结束本段；每产出一条前检查指令数上限。

**策略段（经济/防守/军事三分支）整体保留**：兵源瓶颈→经济（屯田+征兵）；
受威胁且兵少→防守（修城+征兵）；否则军事（士气<30 的部队强制 Rest、本月不出兵；
出击部队兵力<500 不出兵；目标相邻敌城；从部队所在城出发）。常量 500/30 不变。
只修正以下 Amount/余额细节（裁决 6）：

- **Develop**：Amount 固定传 **100**（100 单位银量；结算端公式
  baseCost = BaseDevelopCostSilver × 100 / 100 = BaseDevelopCostSilver）；
  仅当 `res.Silver >= _config.BaseDevelopCostSilver` 时产出（留余量的保守判断）。
  目标仍选 FarmLevel 最低的城。
- **Fortify**：同样 Amount=100，仅当 `res.Silver >= _config.BaseFortifyCostSilver` 时产出。
- **Recruit**：Amount 仍是征兵数（≥1，沿用现有 500/800 上限与兵源池截断）。
  产出前的余量估算必须与结算端占位公式同形：
  `silverNeed = BaseRecruitCostSilver × n / 100`；
  `grainNeed  = BaseRecruitCostGrain  × n / 100 + 2 × n`
  （末尾 `2×n` 是结算端每兵固定附加粮耗；在本文件定义
  `private const int RecruitGrainPerSoldier = 2;` 并注释"与 03 Resolver 占位常量对齐，06 联调锁定"）。
- 三分支内任何新增指令前后都要守上限；不许产出 Amount≤0 的 Develop/Fortify/Recruit。

### 3.3 `src/StrategyGame.AI/Personnel/BestFitPolicy.cs`

**`CheckLoyalty` 改为风险预警**（裁决 2）：
