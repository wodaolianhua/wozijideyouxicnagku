## 2. 精确改动规格（一个方法内两处）

文件：`src/StrategyGame.AI/AiFactionPlanner.cs`

### 改动 A：休整前置（AddStrategicOrders 方法内）

位置：在取得 `cities`/`res`/`armies`/`totalSoldiers` 之后、
`threatened`/`soldierStarved` 判定**之前**，插入最高优先休整检查：

```csharp
// 【v1.5 裁决】休整是士气维护，不受"缺兵/屯田"策略门控：
// 和平腐化 −6/月、哗变每月连发可散兵 30%，等部队进军事分支再休整为时已晚。
// 03 第 6 轮起，本月已休整的部队月度结算挂起腐化（Rest 另给 +3/月，冷却 1 月/军）。
var restArmy = armies
    .Where(a => a.Soldiers > 0
        && a.Morale < MoraleRestThreshold
        && !a.HasRestedThisMonth)
    .OrderBy(a => a.Morale)
    .ThenBy(a => a.Id)
    .FirstOrDefault();
if (restArmy != null && orders.Count < maxOrders)
{
    orders.Add(Order.CreateAiOrder(ActionType.Rest, factionId, restArmy.Id));
    return; // 休整优先，本月不再出屯田/征兵/进攻指令（与 AddMilitaryOrders 既有语义一致）
}
```

说明：
- 与既有 `AddMilitaryOrders` 内第 230 行附近的休整判定**同条件同构造**
  （`MoraleRestThreshold` 常量、`!HasRestedThisMonth` 防冷却拒单、
  `Order.CreateAiOrder(ActionType.Rest, factionId, army.Id)` 三参形式）；
- 多军情景每月只发 1 条 Rest（取士气最低、Id 最小者），保持确定性；
  未来扩军后再议，加一行 `// TODO` 注释即可；
- `return` 是刻意的：休整月不进攻（军事分支本就如此），也不屯田，防止规划器
  在同一份 orders 里经 AddMilitaryOrders 重复加第二条 Rest 被结算端码7（冷却）拒。

## 3. 必须新增的测试（四个场景，沿用既有测试夹具）

1. **v1.5 出兵门禁回归**：己方有 1 城 1 军（Soldiers=6000、Morale=80、
   HasRestedThisMonth=false），势力资源 `Soldier=0`（模拟补给清池后的规划时点），
   存在相邻敌城 → 规划结果包含 **Dispatch**（TargetId=敌城、SecondaryTargetId=出发城）。
   旧代码此场景必走 Econ，本测试是改动 B 的锁。
2. **休整前置（低士气）**：同场景但 Morale=20 → 规划结果**第一条且唯一一条**是
   **Rest**（TargetId=该军 Id），不含 Dispatch/Develop/Recruit。
3. **缺兵仍走经济**：Soldiers=100（<500）、池=0、Morale=80 → 不出 Rest/Dispatch
   （兵力太低时军事分支本就不可达，且高士气不需要休整）；允许 Econ 的 Develop，
   断言以"不含 Rest、不含 Dispatch"为准，不锁 Develop 数量。
4. **无军势力**：己方无任何部队、池有存量（蜀式局面）→ 不出 Rest、不出 Dispatch；
   经济类指令行为与旧逻辑一致（不锁具体数量）。
