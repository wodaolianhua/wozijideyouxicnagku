## 2. 任务一：第 8 步「兵源自动补给」（裁决单 D3）

文件：`StrategyGame.Core\src\TurnPipeline.cs`，现有
`RunSoldierConsumption`（约 252–296 行）是占位实现（只在池归零时加饥荒事件），
把它改造为「补给 + 饥荒」。时点不变：**第 7 步到期指令执行之后、第 9 步 AI 决策之前**。

规则（逐字执行，不要自创编制上限/消耗公式）：

1. 对每个势力，取其所有 `Army.Soldiers > 0` 的部队，按 `Army.Id` 升序；
   `Soldiers == 0` 的部队视为已覆灭，**不补**。
2. 设池存量 `P = faction.Resources.Soldier`，存活部队数 n：
   - `n == 0`：跳过补给（走下面饥荒判定）；
   - `P == 0`：什么都不做；
   - 否则每队先加 `floor(P / n)`，余数 `P % n` 给 Id 最小的前若干队每队 +1；
     然后兵源池归零。
3. **用 delta 表达，禁止裸改**：部队增兵用现有
   `new StateDelta(DeltaTarget.Army, army.Id, DeltaField.ArmySoldiers, old, new)`
   （`DispatchResolver.cs` 约 165/215/229 行有现成写法）；
   池归零用 `DeltaTarget.Faction` + `FactionSoldier`（字段常量
   `Resources.Soldier`，参考 `RecruitResolver.cs` 约 120 行产兵 delta 的写法）。
   走 pipeline 现有的 `ApplyDeltas(state, deltas)` 落地。
4. **饥荒语义随改**：原「`Resources.Soldier != 0` 就跳过，否则饥荒」会在补给后每月误触。
   新条件：**兵源池为 0 且该势力不存在任何 `Soldiers > 0` 部队**才触发饥荒；
   事件构造、`PlaceholderNumbers.FamineMoraleLoss` 数值与 EventKey 全部不变。
5. 不新增 ActionType / 配置项 / 契约字段；注释写清这是 P0 最简链路，
   未来「手动编组/部署」「编制上限」再替换（裁决单已备案）。

确定性：分配只依赖 Id 排序与整数除法，禁止引入随机数。

## 4. 新增测试（双向断言，落 tests 工程）

至少覆盖（测试名可中文，沿用本包风格）：

1. 补给：一池 P 个兵、n 支存活部队 → 每队 floor(P/n)、余数按 Id 升序 +1、池归零；
   再跑一月结果确定（同 seed/同状态两遍逐字段相等）。
2. 补给边界：`Soldiers==0` 的部队不获得补给；池为 0 时部队兵力不变。
3. 饥荒：池为 0 且无存活部队 → 产生 1 条 Famine 事件；池为 0 但有存活部队 → **不**产生。
4. 额度：两方在同一月各成功执行 5 条（上限=5），第 6 条各自被拒
   （`RejectedInsufficientCapacity`）；证明两方计数互不影响。
5. 额度非法方向：单势力第 6 条必拒、月初字典清零后可再次执行 5 条。
6. 深拷贝：`WorldState.Clone()` 后修改副本字典不影响原对象。
