## 第 1 节：恢复只在未参战月生效（**本补丁的核心**）

### 现在的错在哪

`StrategyGame.Core/src/Systems/MoraleSystem.cs` 第 81 行：

```csharp
int morale = army.Morale + _config.MoraleDecayPerMonth;   // ← 无条件 +3
```

「自然恢复」听起来是好事，但它无条件生效时会产生致命后果。

**代入实算**（这就是你报的那个问题的完整版）：

```
第1 月  攻城未决 → 士气 60-3 = 57，  MonthsWithoutBattle 归0
第2 月  攻城未决 → 士气 57+3-3 = 57，  MonthsWithoutBattle 归 0
第3 月  攻城未决 → 57+3-3 = 57
...永远 57，平稳腐化永不触发
```

也就是说：**无脑连续攻城成了最优解**，
「休整 vs 追击」这个本该存在的战略选择根本不存在。

更糟的是，`MonthsWithoutBattle` 在战斗月被归零，
所以和平腐化**在任何有战斗的节奏下都不会触发**——
一个只在"完全不打"时才生效的机制，等于没有。

### 正确规则（三条互斥，按顺序判）

```
本月参战（MonthsWithoutBattle 结算前 == 0）
    → 不恢复，不腐化，只结算战斗士气增减（走 5.4 节那套）
    → MonthsWithoutBattle 保持 0

本月未参战，且 MonthsWithoutBattle < 阈值（4）
    → morale += 3

本月未参战，且 MonthsWithoutBattle >= 阈值（4）
    → morale -= 6
```

**硬约束：恢复与腐化绝对不得在同一个月同时生效。**

### 你要改的地方

`ResolveMonthlyMorale` 里，把无条件 `+ MoraleDecayPerMonth` 换成按上述三分支判断。
方法签名不用变（输入还是 `WorldState`，输出还是 `List<StateDelta>`）。

注意 `MonthsWithoutBattle` 的判定要用**结算前**的值还是**结算后**的值——
设计文档 `4_数值框架.md` 5.2.1 节的语义是
「阈值 4 = 连续 4 个月没打仗就开始腐化」，
所以本月是第 4 个无战月时**当月就扣**，用结算前的值 +1 后比较。
你现在的写法（先 `+1` 再比阈值）是对的，保留。

### 必须新增的测试

| 测试名 | 断言 |
|---|---|
| `TestMorale_参战月不恢复` | 士气 50 的部队连续 3 个月参战，月末士气恰好是 50 − 3×3 = 41，不是 41+9 |
| `TestMorale_连续未参战4月触发腐化` | 士气 60 的部队整月不动，第 4 月末应为 60 + 3+3+3 − 6 = 57（前三月各 +3，第四月 −6） |
| `TestMorale_每2月一战不会恒定在60` | 交替「攻城未决 / 整月休整」跑 12 月，末士气**必须 < 57**，证明腐化能累积 |
| `TestMorale_恢复与腐化不叠加` | 逐月扫描 12 个月，断言没有任何一个月同时出现 `+3` 和 `−6` |

第三个测试是这一节存在的意义——**它直接锁定"无脑连续攻城不再是最优解"**。
写完先自己跑一遍，如果它过了但你没有在测试里断言末士气 < 57，说明测试没测到点上。

## 第 2 节：适配契约 v1.3

契约已改，两处：

### 2.1 `FieldBattleLossFactor` 基准从 6000 订正为 5000

你在战报里问"野战 killRate 注释 0.27 与实算 0.540 不符"——
**你的代码是对的，是文档注释错了**，已订正。

但顺着查下去发现**配置值本身也错了**：

```
lossRate = 0.35 × (6000/10000) × (2 - 2×0.5) = 0.35 × 0.6 × 1.0 = 0.210
```

野战本来应该比攻城**更划算**（没有城墙消耗），
但 0.6 这个乘数把野战攻方的自损抬高了，
削弱了"野战规避城防"这个设计意图。改成 5000 后：

```
lossRate = 0.35 × 0.5 × 1.0 = 0.175   ← 与 3_战斗系统设计.md 3.5 节一致
killRate = 0.27 × 2.0 × 1.0 = 0.540
```

**你的代码不用改**（它读配置，不写死）。
但如果你有测试**断言了 0.210 这个值**，那个测试要改成 0.175。
请grep 你的测试里有没有硬编码的野战期望值。

### 2.2 新增 `ResolveResultCode.RejectedTargetSieged = 10`

设计文档要求区分两种"打不了这个目标"：

| 情况 | 语义 | 玩家应该 |
|---|---|---|
| `RejectedTargetSieged` | 目标**正被围困**（临时状态） | 等下个月，可能就好了 |
| `RejectedTargetOccupied` | 目标**已被其他势力占领**（永久） | 换目标 |

**原来只有一个 `RejectedTargetOccupied`，把两种都塞进去了**，
玩家会以为"打不了"就是永久的，白等一个月。

契约已加`RejectedTargetSieged = 10`，
`ApiContract.ErrorCodes` 也加了 `TargetSieged = "TARGET_SIEGED"`。

**你要做的**：检查你的 Siege 解析器现在对"目标正被围困"返回什么码。
如果返回的是 `RejectedTargetOccupied`，改成 `RejectedTargetSieged`。

如果 03 侧还没有"围困"这个状态（可能它只存在于 City 的某个标记），
**不要自己加这个状态**——上报给我，这可能是契约缺口。
