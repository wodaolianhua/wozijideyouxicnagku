## 返工清单

### 2.1 【核心】战斗公式改为攻守两条独立公式

你上一轮把守方损失改成了 `攻方投入 × lossRate × 0.6`。

**方向对，但只解决了一半**——攻守仍然共用一个 `lossRate`，
这会推出"强将降低 lossRate → 守方更抗打 → **强将反而破城更慢**"。
这是个更隐蔽的逻辑倒错。

**正式方案**（已写入 `3_战斗系统设计.md` 3.1/3.2 节，以那里为准）：

```
# 攻方战损率：攻方每投入 1 点兵力，自己损失多少
lossRate = (BaseLoss / 10000) × (0.5 + 城防/1000) × (2 - 2 × commanderRatio)

# 守方被歼率：攻方每投入 1 点兵力，能打掉多少守军
killRate = (BaseKill  / 10000) × (2 - 城防/1000) × (2 × commanderRatio)

攻方损失 = 投入 × lossRate
守方损失 = min(投入 × killRate, 守城兵力)
```

**注意两个式的方向相反且都是必须的**：

| | 城防↑ | 统帅强↑ |
|---|---|---|
| `lossRate`（攻方自损） | ↑ 更亏 | ↓ 更省 |
| `killRate`（打掉守军） | ↓ 更难打 | ↑ 更快打 |

**契约字段**：`BaseLoss` = 3500，`BaseKill` = 2700。全部走配置，禁止硬编码。

**为什么守方损失按"攻方投入"算而不是按"守军规模"算**：
守军规模没丢——它是攻陷判定的右端（`投入 × killRate ≥ 守军`），
守军越多需要投入越大。守军规模决定**门槛**，守方伤亡决定**每次换掉多少**，
两者是同一道除法的分母和分子，**不该重复相乘**。
如果再乘一次守军规模，会得到"守军 1000 时需 lossRate ≥ 1.0"这种不可达条件。

### 2.2 判定顺序：先击退，后攻陷

```
1. lossRate >= 0.70        → 击退，攻方退回原城
2. 守方损失 >= 守城兵力     → 攻陷，城易主
3. 都不是                  → 未决
```

**顺序不可调换**：若先判攻陷，`lossRate` 已 ≥ 0.70 的强攻在守军恰好被打光时
会同时满足两个条件，顺序不同结果就不同。

### 2.3 未决不重复扣兵

原实现里"守方损失"和"未决双方各损 10%"重复计算了。
现在未决**按正常公式结算，不再额外扣**。`StalemateLossRate` 字段已废弃。

被围困城标记 `Siege`，下月不可再对该城Dispatch，返回 `RejectedTargetSieged`。

### 2.4 `commanderRatio` 去掉 `+1`

你在汇报里问 `5_指令字典.md` 的 `攻/(攻+守+1)` 和 3.1 的`攻/(攻+守)` 哪个对。

**`攻/(攻+守)` 对，`+1` 是错的。**

理由：`+1` 会在双方统帅悬殊时把比值强行拉向 0.5，恰好抹掉"强将/弱将"的差异。

**全项目统一为 `攻 / (攻 + 守)`，两边皆 0 时取 0.5。**
检查 `BattleSystem` 全部调用点。

#### 三个必须踩准的实现细节

**① 低士气惩罚要在比较阈值之前乘上，且不得钳制**

```
lossRate = 公式值 * (GetMoralePenalty() / 10000)   // 倍率 1.0 / 1.5 / 2.5 / 4.0
然后再判断 lossRate >= SiegeThresholdLoss
```

**不要写 `lossRate = Math.Min(lossRate, 1.0)`**。
一旦钳制，士气倍率最多只能把 lossRate 推到 1.0，
永远不会改变"是否 ≥0.70"的判定结果，低士气就等于没惩罚。

**倍率档位是代入实算定出来的**。初稿 ×1.2/1.5/2.0 代入实测后发现：
士气从 60 掉到 10，**战局结果一次都没变**（仍是攻陷，只是多烧兵）——
士气系统形同装饰。现档 ×1.5/2.5/4.0 能让士气 20 时均势攻城从攻陷翻成击退。
`Army.GetMoralePenalty()` 已按新档实现，直接调用即可。

**② 部队士气 vs 势力民心，两个不同的东西**

| 字段 | 所在 | 含义 | 影响 |
|---|---|---|---|
| `Army.Morale` | 每支部队 | 部队士气 | 战损倍率、哗变 |
| `Resources.Morale` | 势力（全势力一个值） | 势力**民心** | Stability、兵源产出 |

**契约里两个字段同名 `Morale` 但不是一回事。**
实现时请用 `army.Morale` 与 `popularity` 区分命名，并在代码里加一行注释提醒后来人。

**③ 士气为 0 触发哗变，用 `HasMutiniedThisMonth` 防重复**

```
若 Army.Morale <= 0 且 !HasMutiniedThisMonth：
    兵力 -= 兵力 * (MutinyRoutRate / 10000)
    产生 EventRecord
    HasMutiniedThisMonth = true
```

### 2.9 一个重要的设计转向（影响你 EconomySystem 的取舍）

早期文档写"348 粮养 3.4 万人"，**这是算术错误**，实际是 1.74 万人。

**粮不是真正的瓶颈，兵源才是。**

| 约束 | 真实压力 |
|---|---|
| 粮草 | 348 粮能养 1.74 万兵 —— 相对宽松 |
| **兵源** | 3000 人口城每月只产 **90 兵**（`3000 × 5000/10000 × Stability/100`），攒 5000 兵要 4 年 |
| **失城** | 人口归零 → 粮产 + 兵源一起腰斩 |

**含义**：压迫感不来自"饿肚子"，来自**"人不够"**和**"打下地也守不住"**。

这直接影响两点：
1. 饥荒事件应该**很难自然触发**，它是极端情况的兜底，不是常驻机制
2. `Stability` 的重要性高于粮储——它直接乘在兵源产出上

**不要**把 EconomySystem 写成"粮不够就崩"的模型。
真正的瓶颈是 `SoldierPerPopPerMonth × Population × Stability`。
