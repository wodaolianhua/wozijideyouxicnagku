## 3. 后端 API（00 定死，前端照此对接；JSON 一律 System.Text.Json 默认 camelCase）

- 通用：`WorldState` 直接序列化（契约类型可 JSON 往返，存档测试已证）。
  启动即 `app.Urls.Add("http://localhost:5178")`（仅 http，不用 HTTPS，免证书）；
  静态文件 + 默认页走 `wwwroot/`。会话对象单例（静态字段 + `lock`），所有端点串行访问。
- **POST /api/new-game** body `{"seed":12345}`（缺省 12345）：
  `new SimulationHost(seed, 120)`（第三参 applySeedVariance 用默认 true），
  置 `State.Factions[0].IsPlayer = true`。重复调用即重开。返回 `{"state":...,"meta":...}`。
- **GET /api/state** → `{"state":...,"meta":...}`；
  `meta = { monthsElapsed, isFinished, winnerFactionId, gameOverReason, upstreamGameOverMonth, upstreamGameOverReason, pendingCount }`
  （全部读宿主公共属性）。
- **POST /api/order** body `{"action":"Recruit|Fortify|Develop|Dispatch|AssignPost|Rest","targetId":N,"secondaryTargetId":N,"amount":N}`：
  - **仅入队不结算**。执行月 = `SimulationHost.NextMonth(State.Year, State.Month)`
    （铁律：入队时执行月必须是当前年月的**下一月**，宿主自己的 AI 入队同款口径）；
  - `OrderId` 由后端从 **100000** 起自增分配（避开 AI 编号空间；本轮无存档，编号语义从简，已备案）；
  - 构造链：`Order.CreatePlayerOrder(action, targetId, amount, secondaryTargetId)` →
    设 `ExecuteYear/ExecuteMonth/OrderId` → `State.PendingOrders.Add(order.ToPendingOrder())`
    （`ToPendingOrder()` 是 StrategyGame.Core `OrderExtensions` 的扩展方法）；
  - 返回 `{"queued":true,"pendingCount":N}`；action 字符串无法解析 → 400；
  - **后端不做任何合法性预校验**（合法性全归 Resolver；码 8 也原样放行，让玩家看到真实拒绝原因）。
- **POST /api/tick**（锁内按序）：
  1. 若 `host.IsFinished` → 400 `{"error":"GAME_OVER"}`；
  2. `int before = State.EventLog.Count;` 并快照「本月将结算的队列」= `State.PendingOrders`
     中 `ExecuteYear/ExecuteMonth == NextMonth(当前年月)` 的指令（按队列序，含 AI + 玩家）；
  3. `host.RunMonth()`；
  4. `turn.Results` 与快照**顺序一一对应**（流水线按 PendingOrders 队列顺序逐条结算、
     一条一个结果——06 宿主 RecordResults 同机制）；断言 `results.Count == 快照条数`，
     不等 → 停手写疑问条；
  5. 本月事件 = `State.EventLog` 从 `before` 到末尾的**增量**。
     **陷阱**：`turn.Events` 是累计量不是本月增量（03 备案），禁止直接用；
  6. 返回 `{"year","month","results":[{"orderId","actorType","action","code","message","deltas"}...],
     "events":[EventRecord...],"meta","state"}`。
- 除上述端点外不加任何东西（无存档/读档/多会话端点）。

## 4. 前端要求（覆盖 README R1–R6）

- 技术栈只许 **pixi.js 8.x + vite + typescript**，禁止 React/Vue/jQuery 等其他运行时依赖。
- `Core/Types.ts`：与后端 JSON 对齐的手写 interface（state/meta/results/events），不引入代码生成。
- **R1 状态镜像**：`GameStateStore` 拉取 `/api/state` 缓存为只读；所有组件从 store 读；
  组件不得持私有副本自行修改。
- **R2 指令唯一入口**：所有操作经 `OrderSender` → `GameClient` → `/api/order`。
  UI 文案必须讲清「**下令成功 ≠ 执行成功**：指令已排入下月，成败看下月结算的 code/message」；
  结算后失败的指令必须把中文 `Message` 显示出来，不许点了没反应。
- **R3 战略地图**：PixiJS Graphics。契约 `City` **没有坐标字段**——00 裁决：
  允许 UI 内置一张**仅布局用**静态坐标表（按城 Id），这是「禁硬编码业务数据」的唯一豁免，
  写进汇报；城名/归属/人口/城防/首都等一律从 state 读。相邻连线按 `AdjacentCityIds`；
  选中城高亮并标出相邻城；悬停显示关键信息。
- **R4 双层视角**：界面明确呈现「上帝视角 / 亲自视角」双入口；亲征按钮点击提示
  「实时战斗将在后续版本开放」。
- **R5 回合结算**：结算面板展示本月 `events`（中文 Message）+ 玩家指令成败（code/message）+
  数值变化（`deltas` 的 targetType/field/old→new）；「继续」按钮进入下月。
- **R6 人才面板**：列出 Name/Specialty/Command/Governance/Loyalty/Post/PostCityId；
  **任命/换任**用 AssignPost，语义照 04 范例：`TargetId=OfficerId、Amount=-1、
  SecondaryTargetId=岗位所在城Id`（岗位类型由 Resolver 决定，契约 Order 没有岗位字段，前端不传）；
  赏赐置灰（见第 0 节）。
- 势力配色写进 `Theme.ts`（建议汉青/魏蓝/蜀红一类可区分三色）。
- 铁律（验收会抽查）：UI 层不得对 state 字段赋值、不得有资源/伤害计算公式；
  业务数据禁止硬编码（布局坐标表唯一豁免）。
