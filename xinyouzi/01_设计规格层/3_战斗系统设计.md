# 战斗系统设计（原型阶段：回合制批量结算）

> **本阶段不做实时战斗。** 本文设计回合制批量结算——一次 `Dispatch` 指令，几个月内算完，产出结果。
> 实时战斗（05B）会在玩法验证通过后单独设计，届时以本文的公式为基础做扩展。
>
> **所有公式必须给出可代入的具体数字。** 不允许出现"待定"。数值依据写在一旁的表格里。

---

## 一、设计目标

原型阶段的战斗只需要回答一个问题：**这次攻城该不该打、能不能打赢、代价多大。**

不做的事：逐秒战斗、动作判定、技能释放、兵种克制链。

### 为什么回合制是对的

| |回合制（现在） | 实时战斗（05B） |
|---|---|---|
| 能否被 Tick 推进 | 能 | **不能** |
| 无头模拟能否跑 | 能 | 不能 |
| 存档复杂度 | 低 | 高（要存战局中间态） |
| 状态回滚 | 容易 | 困难 |
| 玩家决策频率 | 每月一次 | 秒级 |

回合制是原型的正确选择，不是妥协。

## 二、基础模型

### 攻守对比

一场攻城战的结果只取决于四个输入：

```
守方防御力 D_def = 城防值 + 城防等级加成 + 守将加成
攻方攻击力 D_atk = 兵力 × 统帅加成 × 地形加成 × 特长加成
```

### 三种结果

| 结果 | 触发条件 | 后果 |
|---|---|---|
| **攻陷** | 战损率< 阈值且守城兵力归零 | 城易主，攻方获得城池 |
| **击退** | 战损率 ≥ 阈值 | 攻方损失部分兵力，被退回原城 |
| **鏖战未决** | 双方都没达到条件 | 双方各损少量，下月可再战 |

**必须有"未决"结果**：如果只有胜/负两种，AI 会陷入反复攻击同一座城直到打下来或全军覆没。加入未决让"打不下来就走"成为理性选择。

## 三、公式

### 3.1 攻方战损率与守方被歼率（两条独立公式）

**核心认知：攻方损耗和守方伤亡是两个独立的量，不能共用一个 lossRate。**

早期版本用单个 `lossRate` 同时算两边，结果出现两个致命问题：

1. 数学不可达——`守方损失 = 守军 × lossRate × 0.6` 要让守军归零需 `lossRate ≥ 1.667`，
   但击退阈值只有 0.70，**攻陷分支永远不可能触发**，与第七节"三结果全部可达"直接矛盾。
2. 逻辑倒错——共用一个系数后，lossRate 变小（强将）会同时让守方更抗打，
   出现"强将反而破城更慢"的荒谬结论。

因此改为两条独立公式，各管一件事：

```
# 攻方战损率：攻方每投入1 点兵力，自己损失多少
defenseFactor  = 城防值 / 1000.0
commanderRatio = 攻方统帅 / (攻方统帅 + 守方统帅)      # 两边皆 0 时取 0.5
lossRate = 0.35 × (0.5 + defenseFactor) × (2 - 2 × commanderRatio)

# 守方被歼率：攻方每投入 1 点兵力，能打掉多少守军
killRate = 0.27 × (2 - defenseFactor) × (2 × commanderRatio)
```

注意两个式的方向相反且都是必须的：

| | 城防↑ | 统帅强↑ |
|---|---|---|
| `lossRate`（攻方自己损失） | ↑ 更亏 | ↓ 更省 |
| `killRate`（打掉守军） | ↓ 更难打 | ↑ 更快打 |

**`commanderRatio` 口径（全项目唯一）**：`攻 / (攻 + 守)`，不带+1。
曾出现 `攻/(攻+守+1)` 的写法已废弃——`+1` 会在双方统帅悬殊时把比值强行拉向 0.5，
恰好抹掉"强将/ 弱将"的差异，是错的。

**取值校验表**（数字为按上式实算，非估算。`baseLoss=0.35`、`baseKill=0.27`）：

| 情况 | 投入 | 守军 | 统帅(攻/守) | 城防 | lossRate | killRate | 攻方损失 | 守方损失 | 结果 |
|---|---|---|---|---|---|---|---|---|---|
| 均势攻城 | 3000 | 1000 | 50/50 | 500 | 0.350 | 0.401 | 1050 | 1000 | **攻陷** |
| 强将攻城 | 3000 | 1000 | 75/50 | 500 | 0.280 | 0.481 | 840 | 1000 | **攻陷** |
| 弱将攻城 | 3000 | 1000 | 40/50 | 500 | 0.389 | 0.356 | 1167 | 1000 | **攻陷** |
| 兵力不足 | 1200 | 1000 | 50/50 | 500 | 0.350 | 0.401 | 420 | 481 | **未决** |
| 兵力悬殊 | 800 | 1000 | 50/50 | 500 | 0.350 | 0.401 | 280 | 320 | **未决** |
| 死攻坚城 | 3000 | 1000 | 50/50 | 1500 | 0.700 | 0.134 | 2100 | 400 | **击退** |
| 强将死攻 | 3000 | 1000 | 75/50 | 1500 | 0.560 | 0.160 | 1680 | 481 | **未决** |
| 守军坚城 | 2000 | 4000 | 75/75 | 800 | 0.455 | 0.320 | 910 | 641 | **未决** |

**设计意图**：
- 均势下需约 **3 倍于守军的兵力**才能攻陷（3000 攻 1000）。这是扩张的核心门槛。
- **强将的价值有了双重体现**：攻方少损 210（1050→840），且守方被歼更快（0.401→0.481）。
  弱将则攻方多损 117。三个统帅档次的攻防表现全部不同——这正是"用人"玩法的量化落点。
- 死攻坚城 lossRate 恰为 0.700，压在击退阈值上被判击退——所以要先屯田发展。
  但换强将可以把 0.700 压到 0.560，**从"必败"变成"僵持"**：用人可以把不可能变成可能，
  但不能凭空造优势。
- 兵力不足（1200 vs 1000）判未决而非击退，给了"再攒一个月"的余地，
  避免玩家因为一次计算失误被直接打退。

### 3.2 双方兵力损失

```
攻方损失 = 攻方投入兵力 × lossRate
守方损失 = min(攻方投入兵力 × killRate, 守城兵力)     # 上限截断，不会出现负兵力
```

**为什么守方损失按"攻方投入"计而不是按"守军规模"计**：

守军规模并没有丢失——它已经作为攻陷判定的右端出现（`攻方投入 × killRate ≥ 守军`），
所以守军越多，需要的投入越大。守军规模的作用是"决定门槛"，
守方伤亡的作用是"决定每次打掉多少"，两者是这道除法的分子和分母，不该重复相乘。

**城墙保护体现在哪**：体现在 `killRate` 里的 `(2 - defenseFactor)` 项。
城防越高，攻方每点兵力换掉的守军越少；同时城防还抬高`lossRate`。
城墙的价值是双向的——让攻方更亏、同时让守方更抗打——而不是单方面减少守方损失。

**为什么不再给守方一个 0.6 保护系数**：如果守方损失低于攻方，
"龟缩不战"会成为占优策略（守城无风险）。现在守方被歼率 0.401 略高于攻方战损率 0.350，
守方略亏一点，但它有城墙加成（`2 - defenseFactor`）已经把风险压低，
攻方却要额外吃 `(0.5 + defenseFactor)` 的城防惩罚。攻防两端的压力差已经足够，
不需要额外系数。

### 3.3 统帅加成

```
统帅值 = 基础值 × (1 + 专长加成 + 岗位加成)
```

| 来源 | 效果 |
|---|---|
| Officer.Command | 基础统帅值（0-100） |
| PlayerProfile.Command | 玩家亲征时的统帅值 |
| Siege 专长 | 攻城战 lossRate ×0.85 |
| Cavalry 专长 | 野战 lossRate ×0.85 |
| Logistics 专长 | 该部队每月士气衰减 -50% |
| Agriculture 专长 | 不影响战斗，但所在城粮产 +30% |

**关键**：玩家亲征时**不叠加任何 Officer 加成**（见设计决策 D9）。玩家赢在个人能力，人才赢在组合。

### 3.4 攻陷判定（判定顺序不可调换）

```
1. lossRate >= 0.70          → 击退，攻方退回原城，双方损失照算
2. 守方损失 >= 守城兵力       → 攻陷，城易主
3. 以上都不是                 → 未决
```

**为什么"击退"必须放在最前**：如果先判攻陷，`lossRate` 已经 ≥ 0.70 的强攻
在守军恰好被打光时会同时满足两个条件，顺序不同结果就不同。所以先判击退——
**攻方打不动就先撤，别在无意义的消耗里把部队送光**。

**未决的处理**：按 3.2 算出的双方损失照常结算（不额外加10%），
被围困城标记 `Siege`，下个月不能再对该城发起 Dispatch，返回 `RejectedTargetSieged`。

### 3.5 野战（两军对撞）

不涉及城池时使用。野战没有城防，所以 `defenseFactor = 0`，
`(2 - defenseFactor)` 从 1.5 变成 **2.0**，`(0.5 + defenseFactor)` 从 1.0 变成 **0.5**：

```
lossRate = 0.35 × 0.5 × (2 - 2 × commanderRatio)     # 0.175（均势）
killRate = 0.27 × 2.0 × (2 × commanderRatio)         # 0.540（均势）
```

> ⚠️ **注意注释里的数字**：`killRate` 写的是基础系数 0.27，
> 但因为野战 `(2 - defenseFactor) = 2.0`（攻城只有 1.5），
> **实算结果是 0.540**，不是 0.27。
> `lossRate` 同理，实算 0.175 而非注释里的 0.21。
> （这处注释错误由 03 包执行者在实现时发现，已订正。）
> `FieldBattleLossFactor` = 5000（0.5），因为 `BaseLoss × 0.5 = 0.175`，
> 这才是"野战比攻城安全"（0.175 vs 0.35，正好一半）的来源。

**野战需要多少兵力才能全歼对方**（实算，均势统帅）：

```
需要投入 = 守军 / killRate = 守军 / 0.540 ≈ 1.85 倍守军
```

对比攻城需要约 **2.5 倍**守军。

**所以"避开坚城、诱敌野战"确实是更划算的策略**——
这正是设这套系数想要的设计意图。如果实测下来野战过于强势
（AI 全部绕开攻城野战滚雪球），把 `FieldBattleLossFactor` 调低即可。

野战判定同攻城，只是没有"城易主"，结果只有两种：**击退 / 未决**
（野战没有攻陷，也就没有夺城）。击退条件仍是 `lossRate ≥ 0.70`，
均势野战 lossRate 0.175，永远达不到阈值——这意味着
**野战几乎总是"未决"**，双方各自损耗后拉开距离，下月可再战。

## 四、经济与战斗的关系

这是本设计的关键部分：**战斗不是孤立的，它和经营系统互相咬合。**

```
屯田 → 粮产 → 征兵 → 兵力 → 攻城 → 得城池 → 更多人口 → 更多粮产
                    ↑                                    │
                    └────────修城防 ←──────────────────┘
                          （让下一次攻城更难被打）
```

### 粮耗压力

部队每月消耗粮食：

```
月耗粮 = 兵力 × 0.02
```

**设计意图**：5000 人每月耗 100 粮。而一座 3000 人口的城屯田满级只产348 粮
（详见 `4_数值框架.md`），意味着养5000 人需要一座城的全部产出还多。

如果屯田跟不上，玩家会陷入"越打越穷"。这是有意的——**它逼玩家不能无脑扩张，必须算清楚账**。

**校验**：三城满屯、养 3 万兵，月耗 600 粮，产出约 1000 粮。看起来还有余，
但一旦战败损失城池，产出会立刻腰斩，压力骤增。

### 兵源与灾荒

```
本月兵源产出 = 人口 × SoldierPerPopPerMonth × (Stability / 100)
Soldier归零后连续 3 个月 → 饥荒事件
```

如果 `Stability` 掉太低（民心动摇），兵源产出下降 → 更容易陷入饥荒。**这是"打太多仗会亡国"的机制保证**，让扩张有天然刹车。

## 五、胜负判定

| 条件 | 结局 |
|---|---|
| 玩家仅剩 1 座城 | 失败 |
| 玩家全部城池易主 | 立即失败 |
| 玩家拥有大陆 80% 以上城池 | 立即胜利 |
| 存活满 72 个月（6 年） | 按城池数排名结算 |

**关于目标时长**：用户期望约 5 年（60-72 回合）。因此：
- 60 个月：及格线——多数玩家应该在此前后分出胜负
- 72 个月：硬上限——超时强制按城池数结算，避免拖成消耗战

## 六、与实时战斗（05B）的衔接

原型阶段的战斗是"一次结算"，实时战斗是"一段过程"。衔接方案：

```
Dispatch 指令
    ↓
Resolver 判断：这是普通攻城还是需要实时战斗？
    ↓
├── 普通攻城 → 用本文的公式批量结算（当前实现）
│
└── 实时战斗 → 打开战斗场景（05B）
                 ↓
             战斗结束，产出 StateDelta
                 ↓
             StateApplier 统一写回（与回合制走同一条路径）
```

**关键约束**：实时战斗的结果也必须以 `StateDelta` 形式产出，走和回合制**完全相同**的写回路径。不能让实时战斗成为旁路。

**公式复用**：实时战斗的伤害模型应该与本文的战损率公式保持一致（同一套系数，不同的表现形式）。如果实时战斗自己写一套伤害计算，就会出现"回合制说打赢、实时打输了"的荒谬情况。
