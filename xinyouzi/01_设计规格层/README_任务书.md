## 这是什么

本包产出**全部设计文档**，是整个项目的上游。**除02 包外，所有编码工作都阻塞在本包定稿之上。**

这不是"写文档给人看"，而是**把设计转成可以直接翻译成代码的规格**——枚举值、公式、字段表必须具体到能照抄。

如果玩法不定就写代码，规则内核写完后会发现指令类型不够用、状态字段漏了、时间粒度选错——整个 03 包要重写。**宁可慢两周，不要返工一个月。**

## 逐条需求

### R1 世界观

必须回答：

- 什么时代背景？（例如三国、架空战国、近代早期）——**会影响所有术语命名**
- 玩家扮演的将领是谁？起点是什么规模的势力？（建议：中等势力，可败可胜）
- 玩家是"君主"还是"将领"？两者的权限边界在哪？
- 世界地图是真实地理改编还是完全架空？——**决定地图数据怎么建**
- 一共几个势力？原型阶段做 3 个（玩家 + 2 个 AI），其余留接口

### R2 核心玩法拆解

必须产出**玩法优先级清单**，格式：

| 模块 | 优先级 | P0 阶段做什么 | 依赖 |
|---|---|---|---|
| 征兵 | P0 | 消耗粮银，季度产兵 | 数值框架 |
| 修城 | P0 | 提升城防，降低被攻破概率 | 战斗系统 |
| 屯田 | P0 | 提升粮产 | 数值框架 |
| 出兵 | P0 | 攻守判定，回合制结算 | 战斗系统 |
| 任命人才 | P0 | 岗位加成生效 | 人才特质表 |
| 实时战斗 | P2 | 原型不做 | — |

**双层视角切换规则**必须明确写出：什么条件下玩家能亲自上阵、上阵时是否暂停回合、上阵中能否下达宏观指令。这是本项目最独特的设计点，必须先想清楚。

### R3 战斗系统设计

原型阶段（回合制批量结算）必须给出完整公式：

```
攻方剩余兵力 = 攻方兵力 × (1 − 战损率)
战损率 = f(攻方兵力, 守方城防, 统帅加成, 地形, 士气)
```

**每个系数必须填具体数值**，并说明"为什么是这个数"。

同时必须预留实时战斗接口：

- 实时战斗如何被一条 `Dispatch` 指令调用？
- 战斗中玩家战败，回合状态如何回滚？
- 是否需要"战斗进行中"这个中间世界状态？（建议：需要，`Army.Stance = Moving/Besieging`）

### R4 数值框架

必须定义**平衡目标**，否则调数值没有方向：

- 一局目标时长：多少回合
- 玩家初始资源：粮 / 银 / 兵源 / 人口
- 一个城池每季度产出：粮 / 兵
- 攻城战需要的兵力倍数关系

所有数值写入 `4_数值框架.md`，格式为表格：数值名 / 初始值 / 增长方式 / 依据。

### R5 指令字典（最重要）

这是设计层与代码层的直接交界面，必须**穷尽**。每条指令按下表填写：

```
### ActionType.Dispatch（出兵）
- 语义：将领率军从 A 城向 B 城移动并发动进攻
- ActorType：Player / Officer / AiFaction（全部允许）
- TargetId：目标城池 Id
- SecondaryTargetId：出发城池 Id
- Amount：投入兵力
- 前置校验：出发城池归属、兵力充足、相邻、统帅存在
- 结算产出：StateDelta（兵力变化、城防变化）+ EventRecord
- 依赖：战斗系统公式
```

**至少覆盖**：征兵、修城、屯田、出兵、任命人才、休整。这六条是P0，必须详细到能直接写 Resolver。

### R6 WorldState 字段表

对核心契约 v1.0 中每个字段补充：含义、取值范围、默认值、何时变化。

如果发现字段不够用，**提出新增申请**（列清楚字段名、类型、用途），但不要直接改核心契约。
