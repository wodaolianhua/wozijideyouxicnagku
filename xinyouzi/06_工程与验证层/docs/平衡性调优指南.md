> **怎么用这份文档**：先跑模拟拿数据 → 对照指标表 → 定位疑似成因 → **写变更申请等裁决**。
> **不要直接改 `BalanceConfig`**。数值表归 02 包，改动走 00 项目管理的变更流程。
>
> 配套命令（在本包目录下）：
>
> ```bash
> dotnet run --project src/StrategyGame.Tools -- simulate --games 1000 --seed 12345
> dotnet run --project src/StrategyGame.Tools -- analyze          # 从 CSV 重出报告
> dotnet run --project src/StrategyGame.Tools -- replay --seed 12345
> ```

## 1. 流水线：改数值 → 看结果

```
改 02 包 config.json（或 SampleData.CreateBalance）
    ↓
dotnet run --project src/StrategyGame.Tools -- simulate --games 1000 --seed 12345
    ↓
out/result.csv            逐局明细（Excel 分析用）
out/平衡分析_第3轮.md      聚合指标（人看用）
    ↓
对照下方指标表 → 定位疑似成因 → 写变更申请
```

**默认基线**：1000 局、seed 12345、120 月、并行。
**基线可复现性**：同参数重跑，CSV 字节级一致（种子 = baseSeed + gameIndex）。

## 2. 指标含义与调整方向

### 2.1 第一轮指标（粗筛，判断「游戏有没有在跑」）

| 指标 | 含义 | 参考区间 | 偏离含义 | 优先查哪里 |
|---|---|---|---|---|
| **基准槽位胜率** | 槽 0 在三方 AI 混战中的胜场占比 | 25%–45%（**仅参考，非真实玩家**） | 过高 = 槽 0 初始条件占优；过低 = 槽 0 处于劣势或全局僵持 | 先看僵持率：僵持率高时胜率必然被压低，不是独立的 AI 强度问题 |
| **平均存活/终局月数** | 每局推进到终局的月数均值 | ≥ 60 | 太低 = 开局崩盘或早早被灭；太高 = 打不完 | `VictoryChecker` 口径、三方兵力对比 |
| **10 回合内终局比例** | 前 10 月就分出胜负的局占比 | 接近 0 | 明显 > 0 = 开局滚雪球或开局崩盘 | 初始资源档位、初始兵力 |

### 2.2 第二轮指标（真正的调平衡抓手）

| 指标 | 含义 | 参考区间 | 偏离含义 | 优先查哪里 |
|---|---|---|---|---|
| **平均兵源存量** | 势力 `Resources.Soldier`（可用兵源池）的月均值 | 应长期偏低 | 长期偏高 = 兵源压力不够，满编扩张；归零 = 产能崩盘 | `SoldierPerPopPerMonth`、`StabilityDecayPerMonth`、`ResolveSoldierIncome` |
| **AI 部队士气分布** | `Army.Morale` 的样本均值与低士气占比 | 均值不应长期 <30 | 长期 <30 = 「和平腐化」压过恢复，Rest 逻辑没生效 | `MoraleSystem`、AI 策略优先级、`MaxOrdersPerFactionPerMonth` |
| **攻陷次数 / Dispatch 尝试次数** | 攻城成功率 | 30%–50% | 过高 = 守方形同虚设；过低 = 永远打不下来 | `BaseLoss` / `BaseKill` / `SiegeThresholdLoss` / 城防值 |
| **僵持率（120 月未决占比）** | 跑满月数仍未分出胜负的局占比 | 20%–40% | 过高 = 无人能攻下任何城（兵力门槛或战斗公式问题） | 兵力转化链路、出兵安全线、攻城门槛 |
| **各类拒绝码占比** | 每个 `ResolveResultCode` 的分布 | 全数列出，异常偏高点名 | 某码占比畸高 = 对应策略反复撞墙 | 见下方 2.3 |

### 2.3 拒绝码速查

| 码 | 枚举 | 常见成因 |
|---|---|---|
| 0 | `Success` | — |
| 2 | `RejectedNoResources` | 银/粮不足；**若占比高，说明征兵成本公式与实际产出脱节**（见第 8 节备案 1 的双语义问题） |
| 5 | `RejectedNoPost` | 目标城池已有在岗人才（一城一岗） |
| 7 | `RejectedCooldown` | 本月已休整过 / 重复操作 |
| 8 | `RejectedNotImplemented` | **必须恒为 0**。非 0 = 链路存在非法行动，测试红掉 |
| 9 | `RejectedInsufficientCapacity` | 本月指令额度用尽。**三方混战下占比高是必然的**——`ActionsThisMonth` 是全局单计数而上限按势力（见 D4） |
| 10 | `RejectedTargetSieged` | 目标城正被围困，下月再试 |

## 3. CSV 列速查

`out/result.csv` 共 47 列，UTF-8 带 BOM，Excel 直接打开。

| 列 | 含义 |
|---|---|
| `game_index` / `seed` | 局序与本局种子（seed = baseSeed + game_index） |
| `winner_faction` | 胜方势力 Id；-1 = 无胜方（僵持） |
| `game_over_reason` | 终局原因稳定标识符：`Elimination` / `Stalemate` |
| `months_survived` | 本局推进月数 |
| `faction{N}_cities` | 终局时该势力的城池数 |
| `faction{N}_soldiers` | 终局时该势力全部部队的总兵力 |
| `faction{N}_grain` / `_silver` | 终局时该势力的粮 / 银 |
| `faction{N}_soldier_stock` | 终局时该势力的可用兵源池 |
| `orders_{行动类型}` | 各行动类型的发起次数（含被拒的尝试） |
| `orders_total` | AI 指令总数 |
| `reject_{码名}` | 各类结算结果码的计数 |
| `mutiny_count` / `city_captured_count` | 哗变次数 / 攻陷次数 |
| `avg_army_morale` | 部队士气样本均值 |
| `low_morale_ratio_permille` | 低士气（<30）样本占比（万分比） |
| `faction{N}_avg_soldier_stock` | 该势力的月均兵源存量 |

## 4. 常见问题的排查路径

### 4.1 僵持率 100%（无一方能攻下任何城）

按顺序排查：

1. **看 `orders_dispatch` 是否为 0**。为 0 = AI 从未尝试出兵。
2. **为 0 则看 `AiFactionPlanner.AddMilitaryOrders` 的进入条件**：
   - `totalSoldiers >= SoldierSafetyThreshold`（当前 500）——用的是**部队现有兵力** `Army.Soldiers`；
   - `army.Soldiers >= SoldierSafetyThreshold`。
3. **若部队兵力永远低于阈值**，查兵源 → 部队兵力的转化链路：
   `ResolveSoldierIncome` 与 `RecruitResolver` 加的都是 `Resources.Soldier`（兵源池），
   而 `Army.Soldiers` 只被战斗损耗与哗变减少，**从不增加**。链路缺失时出兵分支永不可达。
4. **若 Dispatch 有尝试但攻陷为 0**，查战斗公式：`BaseLoss` / `BaseKill` / `SiegeThresholdLoss`，
   以及 `DispatchResolver` 的攻城兵力门槛与城防值。

### 4.2 部队士气长期 <30

1. 看 `avg_army_morale` 与 `low_morale_ratio_permille`。
2. `MoraleSystem` 的规则：未参战时「恢复 +3 / 连续 4 月无战则腐化 −6」。
   **恢复只在「本月未参战」时生效**，参战当月不恢复。
3. 若长期不参战（因为打不起来），则只腐化不恢复 —— 士气必然崩塌。
4. 看 `orders_rest` 是否为 0：为 0 说明 `Rest` 指令被策略优先级或指令额度挤掉。
5. 修 4.1（能打起来）通常同时修好士气。

### 4.3 某方碾压其余两方

1. 先看 `faction{N}_avg_soldier_stock` 的差距。
2. 若差距来自**初始档位**而非运营能力，说明初始条件不对称 —— 这正是 `WorldVariator` 要消除的。
3. 运营能力差异看 `orders_*` 分布：某方 Develop 远多于其余 = 它在滚雪球。

## 5. 口径纪律（必须遵守）

1. **只报数，不调数值**。报表数字是待裁决的数据点，不是失败。
2. 超区间就如实写「超出区间，疑似……」，并给出**具体到函数名/常量名**的疑似成因。
3. 不替用户说话，不写「建议把 X 调成 Y」——那是设计裁决，不是工程判断。
4. 发现问题写变更申请，等 00 项目管理裁决。
5. **「基准槽位」不是「玩家」**。P0 没有玩家 AI，胜率是三方 AI 混战口径。

## 6. 已知口径说明

- **「基准槽位」（槽 0）**：P0 三方全 AI，槽 0 与其余两方地位对等。
  真正的玩家胜率要等 05A 可玩或未来的脚本玩家策略。
- **种子敏感化默认开启**：上游 `SampleData.CreateWorld(seed)` 只把 seed 存进状态、不消费 seed 生成世界内容，
  严格照抄时 1000 局会跑出完全相同的一局。06 层用 `WorldVariator` 按 seed 轮换上游**已有的**三档初始资源
  （不新增任何数值），让三方初始条件对称化。
  用 `--strict-world` 可复现严格照抄上游的基线行为。
- **事件统计口径**：`TurnResult.Events` 是累计量（上游第 11 步会把整个 `EventLog` 追加进去），
  本工具按 `EventLog` 长度增量统计哗变与攻陷。
- **终局口径**：仅剩 ≤1 个势力仍拥有城池 → `Elimination`；跑满月数上限 → `Stalemate`。
  上游 `VictoryChecker` 是玩家口径，三方全 AI 时不可用，其判定值仅作诊断记录。
