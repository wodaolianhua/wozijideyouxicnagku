# 06_工程与验证层 · 任务书

## 这是什么

本包提供**项目的基础设施**，其中`BatchSimulator`（无头批量模拟器）是整个项目**最有价值的工程资产**。

## 为什么这个包优先级这么高

因为它直接决定**项目迭代速度**。

游戏项目最常见的死法：调一次数值要重新编译、跑一次验证要手动点20 分钟 UI。结果是设计师不敢改数值，或者改了不知道好没好。这个包的存在就是为了解决它。

有了无头模拟器，调平衡的方式变成：

```
改 JSON 数值 → 跑 1000 局模拟（无画面，几分钟）→ 对比胜率与资源曲线 → 再调
```

**这是「用人」这类系统能收敛的根本保障。** 100 个人才的组合搭配不可能手动测，只能靠模拟。

## 逐条需求

### R1 存档系统

- 序列化为 **JSON，不使用二进制**（可调试、可人工检查）
- 必须包含 `Seed`，否则读档后随机序列会变
- 必须包含 `TurnPipeline` 的内部状态（若有）
- 读档后继续模拟，结果必须与存档时一致（确定性要求）

### R2 回放系统

```csharp
replay.Record(state, order, result);   // 记录每一步
var finalState = replay.Replay(seed, orders, months);  // 从头重放
```

**`Replay` 的结果必须与原始模拟的最终状态逐字段相等。** 这是 `Resolver` 纯函数设计的直接检验——如果不相等，说明有地方违反纯函数铁律。

### R3 无头批量模拟器（重点）

```csharp
var report = simulator.Run(seed: 12345, months: 120, aiFactionCount: 2);
// report: 总局数、胜率、平均存活回合数、平均最终资源、平均城池数
```

要求：

- **完全无画面**：不加载任何渲染资源，纯逻辑跑
- **可并行**：用 `Parallel.For` 多核加速（1000 局建议 4核跑 5 分钟内）
- **统计维度完整**：不能只统计胜负，要输出资源曲线和城池数曲线
- **可导出 CSV**，供Excel 分析

**平衡性判断标准**（写进报告）：

| 指标 | 目标区间 | 偏离含义 |
|---|---|---|
| 玩家胜率（vs 2 AI） | 25% - 45% | 太高=AI太弱，太低=平衡有问题 |
| 平均存活回合 | ≥ 60回合 | 太低=玩家容易早期被灭 |
| 首回合终局比例 | 接近 0 | 有明显开局滚雪球或开局崩盘 |

### R4 命令行工具

```bash
dotnet run --project tools/BatchSim -- --games 1000 --seed 42 --months 120 --out report.csv
```

参数：`--games` 局数 / `--seed` 随机种子 / `--months` 月数 / `--out` CSV 输出路径。

### R5 确定性验证

**测试用例**：

```
同 Seed ＋ 同指令序列 → 跑两次 → 最终状态逐字段比对 → 必须完全相等
```

这个测试是整个项目的**信任基础**。它失败意味着整个规则层有隐式状态污染，必须先修。

## 验收标准（DoD）

### 硬性

- [ ] 确定性测试通过（同 Seed 两次模拟最终状态完全一致）
- [ ] 回放测试通过（`Replay` 结果与原始模拟一致）
- [ ] 1000 局 120 月的模拟在 4 核上 5 分钟内跑完
- [ ] 无头模式下不加载任何渲染资源

### 功能

- [ ] 存档/读档往返后状态完全一致
- [ ] 批量模拟报告包含：胜率、平均存活回合、平均最终资源、平均城池数
- [ ] 支持CSV 导出
- [ ] 命令行工具参数齐全
- [ ] 提供一份《平衡性调优指南》，说明每个指标的含义与调整方向

### 边界

- [ ] 不修改 `WorldState` 结构（只读取，不改定义）
- [ ] 不在本包内实现任何游戏规则

## 禁止事项

- 禁止在批量模拟器中加"加速绕过"逻辑（比如让 AI 跳过后几步）——必须真实跑完整流程
- 禁止硬编码模拟参数（全部从命令行/配置传入）
- 禁止使用二进制存档格式
- 禁止在模拟器里修改 `StrategyGame.Core` 的代码——发现问题上报到 03 包
- 禁止输出到控制台的完整状态（只输出统计摘要，否则日志会爆）
