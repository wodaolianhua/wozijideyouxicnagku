## 为什么这个包优先级最高

**这个包决定项目的迭代速度。**

现状是：改一个数值 → 重新编译 → 手动点 20 分钟 UI → 才能看到结果。
设计师试三个数值组合要花一小时，所以**根本不敢调数值**。

做完这个包之后：改 JSON → 跑 1000 局 → 出对比报告 → 5 分钟。

**这是本项目能不能快速迭代的分水岭。** 05A 的 UI 做得再好，
数值调不动也是白搭。

**也正因为它重要，这个包最容易出错的地方是：不要自己调数值来让报表好看。**

## 核心要求

### 6.1 SaveSystem（存档）

JSON 格式，**必须包含 Seed**。

Seed 是确定性的根，存档丢了它整局就无法复现。
还要包含 `DifficultyLevel`（D16：自适应难度只能调数值不能调行为，
这个字段必须持久化，否则读档后难度会变）。

### 6.2 ReplaySystem（回放）

回放结果必须与原始模拟**逐字段相等**。

实现方式：每回合把所有 Order 记进日志，读档时重放这些 Order。
**不要重新让 AI 决策**——那会引入不确定性。

### 6.3 BatchSimulator（无头批量模拟器）

**这是本包最有价值的产物。**

```
跑 N 局（默认 1000）× 120 月，全程无头、无 UI
输出 CSV：每局的胜负、存活回合数、终局城池分布、关键统计
```

### 6.4 命令行工具 + CSV 导出

```
dotnet run --project StrategyGame.Tools -- simulate --games 1000 --seed 12345 --out result.csv
```

## 【核心红线】确定性

**同样���输入必须得到逐字段相同的输出。** 不允许任何"大概差不多"。

| 检查项 | 要求 |
|---|---|
| 确定性 | 同 Seed 跑两次，最终状态逐字段相等 |
| 回放 | Replay 结果与原始模拟逐字段相等 |
| 存档 | 存档读回后继续模拟，结果与未存档时一致 |

**这条一旦破了，整个项目的平衡验证全部作废**——
因为无法判断"这个胜率变化"是设计效果还是随机噪声。

你会遇到的破坏确定性的常见来源：
- `DateTime.Now` / `Guid.NewGuid()` / `Random.Shared`（上游的锅，报出来）
- 迭代 `Dictionary` 时顺序不稳定 → **模拟时一律用 `SortedDictionary` 或先 `OrderBy`**
- 并行模拟时共享了随机源 → **每局必须有独立的随机源实例**

**发现上游违反确定性，先记录并上报，不要自己改 StrategyGame.Core 的代码。**

## 平衡性判断标准（写进报告）

### 第一轮指标

| 指标 | 目标 | 偏离说明 |
|---|---|---|
| 玩家胜率（vs 2 AI） | 25% - 45% | 太高说明 AI 太弱，太低说明平衡有问题 |
| 平均存活回合 | ≥ 60 | 太低说明玩家容易被早期灭掉 |
| 首回合终局比例 | 接近 0 | 太高说明开局平衡崩了 |

### 第二轮指标（这些才是真正调平衡的抓手）

| 指标 | 参考区间 | 说明 |
|---|---|---|
| **平均兵源存量** | 应长期偏低 | AI 如果常年满编扩张，说明兵源压力不够 |
| **士气分布** | AI 士气不应长期 < 30 | 说明它在无脑连续作战，Rest 逻辑可能没生效 |
| **攻陷次数 / 尝试次数** | 30% - 50% | 过低说明打不下来，过高说明战斗公式太宽松 |
| **僵持率（未决占比）** | 20% - 40% | 过高说明胜负判定太模糊 |

## 【重要】报告纪律

**发现问题如实写数字，让数据说话。不要为了让报表好看去调数值。**

理由：
1. 数值是设计层的决定，不是执行层的。你改了没人知道，也没法回溯
2. "玩家胜率 60%" 本身不是失败——**它是一个待裁决的数据点**。
   我会判断该调 AI 还是该调玩家还是该改设计

**正确做法**：报告里写"玩家胜率 62%，超出目标区间，
疑似 AI 决策过于保守，建议检查 IFactionPlanner 的扩张阈值"
**错误做法**：自己去改 `BalanceConfig` 把胜率压到 40%

发现问题写变更申请，不要自己改。
